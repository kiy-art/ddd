# 部署ごとのナレッジと会議の仕組み（2026-10-10、社長の方針）

部署ごとにナレッジを貯める。ふだんは**部単位**で活動し、部署をまたぐ意見交換は**代表者会議（全部署会議）だけ**で行う。
理由は**意見の偏りを防ぐため**。先に出た意見や強い意見に全体が引っぱられないよう、各部署が先に自分の意見を固めてから持ち寄る。

## 日程
- 日付の決め方：定期実行は日本時間0:00に動くので、その回の日付は「12時間前の日付」（`TZ=Asia/Tokyo date -d '-12 hours' +%F`）とする。ファイル名の日付もこれを使う。
- **部内検討**：毎晩24時（定期タスク「PAR 部内検討(毎日)・全部署会議(水・土)」、日本時間0:00に起動）。
- **全部署会議**：毎週水曜・土曜の夜。部内検討のあとに続けて行い、終わったら社長報告。日本時間で木曜・日曜の0:00に動く回が該当する（曜日は12時間前の曜日で判定する：`TZ=Asia/Tokyo date -d '-12 hours' +%u`が3か6）。
- 月曜の週次経営会議は廃止（水・土に置きかえ）。

## 構成
- `00_代表者会議/`：進め方・偏りチェック表（`README.md`）、`議題/YYYY-MM-DD.md`、`議事録/YYYY-MM/YYYY-MM-DD.md`（1回の会議で1ファイル、議題は節）、`_テンプレート/`。書くのは議長だけ
- 部署フォルダ：`01_全体統括`（議長）、`02_営業`、`03_マーケティング`、`04_SE`、`05_人事`、`06_経理`、`07_経営企画`、`08_Webデザイン`、`09_総務`、`10_監査`（立ち会い。賛否は言わない）
- 各部署フォルダ：`README.md`（役割・KPI）、`knowledge.md`（1行1件）、`01_部内検討/`、`02_会議提出/`（意見書。1回の会議で1ファイル`YYYY-MM-DD_代表者会議.md`、議題は節）。`01_全体統括/02_会議提出/`には議長の案、`10_監査/02_会議提出/`には偏りチェック表と監査の判定を置く
- 部署は全事業共通（001_Par.Golf、今後の002、003…）。ナレッジの行には事業番号を付ける。

## 流れ
1. **毎日の部内検討**：各部署が、他部署を見ずに自分のフォルダで検討し、`01_部内検討/YYYY-MM-DD_件名.md`に記録し、学びを`knowledge.md`に追記する。議題も気づきもない部署は「検討事項なし」と1行だけ返して終える（利用枠の節約）。KPIの記録（`backend/scripts/kpi_snapshot.py`）は全体統括が最初に行い、各部署はその台帳を事実として読む。
2. **水・土は続けて全部署会議**（`00_代表者会議/README.md`）：
   - 各部署が意見書を`02_会議提出/YYYY-MM-DD_代表者会議.md`に出す。出したあとは書き換えない（考えが変わったら「会議後」欄に追記）。
   - 議長（全体統括）は、全部署の意見書がそろってから一度に並べる。
   - 発言順は前回からひとつずらす。全体統括は自分の案を最後に出す。
   - 少数意見・反対意見は、理由つきで議事録に残す。
   - 監査は賛否を言わず、偏りチェックだけを行う。
   - 議事録は`00_代表者会議/議事録/YYYY-MM/YYYY-MM-DD.md`。
   - 各部署は、翌晩の部内検討で、結論を自分の`knowledge.md`の「代表者会議から持ち帰ったこと」に書く。
3. **社長報告**：Notionの報告（Code → 社長室）に、判断が必要なことと報告のみを分けて書く（`docs/report_format.md`）。判断が必要な件は判断ボードへ。「部署別の意見」には各部署の意見書の要点を、「社内の意見（まとめ）」には議事録の結論を入れる。

## 専門スキルと、スキルの育成ループ（2026-10-10、社長の方針）
各部署は、自分の専門スキル（`.claude/skills/pro-<部署>/SKILL.md`）を検討の最初に読み、その基準で動く。スキルは使いながら育てる。

| 部署 | スキル |
|---|---|
| 02_営業 | `pro-sales` |
| 03_マーケティング | `pro-marketing` |
| 04_SE | `pro-se` |
| 05_人事 | `pro-hr`（育成係） |
| 06_経理 | `pro-accounting` |
| 07_経営企画 | `pro-strategy` |
| 08_Webデザイン | `pro-webdesign` |
| 09_総務 | `pro-general-affairs` |
| 10_監査 | `pro-audit` |
| 01_全体統括 | `ai-company-meeting`（今のまま） |

### 育成ループ
1. **毎晩（各部署）**：スキルの基準が足りなかった・外れた・古かったら、自分の`knowledge.md`の「スキル改善メモ」に1行で書く。提案が外れた（`proposals.csv`の`hit`）ときは、原因をここに書く。
2. **毎週土曜の代表者会議（各部署）**：意見書の最後に「## スキル改善案」の節を付け、メモから最大3件を出す。偏りを防ぐため、ほかの節と同じく会議前に出し、書き換えない。
3. **同じ会議（人事）**：全部署の意見書がそろってから、議長が各部署の「スキル改善案」の節だけを人事に渡す。人事は評価（採用率・当たり率・差し戻しの理由）と合わせて、部署ごとに最大3か所の改訂案を出す（`pro-hr`の手順）。
4. **監査**：改訂案が法令・安全・秘密情報のルールを弱めていないかを確かめる。弱めるものは差し戻す。
5. **全体統括**：合格した改訂案を各`SKILL.md`に反映し（レベルA。費用なし）、「改訂履歴」に1行足す。結果は`05_人事/スキル評価/<その回の日付>.md`に残し、議事録の「振り返り」に載せる。
- 「土曜の代表者会議」＝曜日の判定（`TZ=Asia/Tokyo date -d '-12 hours' +%u`）が`6`の回。水曜の会議では行わない（利用枠の節約）。
- スキルは短く保つ（目安4,000字以内）。足すときは、古い基準を削る案もあわせて出す（利用枠の節約）。
- 各部署はスキルのファイルを自分で書き換えない。

## 偏りを防ぐ決まり（全部署共通）
1. 部内検討のあいだは、他部署のフォルダを読まない（例外：監査は記録の確認のため全部署を読める。議長＝全体統括は議題づくりのため、各部署の「会議に出したい件」を読める）。読んでよいのは事実のデータ（`docs/knowledge/`の台帳・`market.md`・`learnings.md`、`docs/knowledge/kpi/`）と過去の議事録（`00_代表者会議/議事録/`、`docs/meetings/`）だけ。
2. 自分のフォルダにだけ書く（例外：`00_代表者会議/`は議長だけが書く）。
3. 意見書は会議前に出し、出したあとは書き換えない。
4. 発言順は毎回ずらす。全体統括は自分の案を最後に出す。
5. 少数意見・反対意見は消さない。
6. 監査が偏りをチェックする。
7. 他部署の学びは、代表者会議の議事録を通してだけ取り込む。

## 変わらないこと
- 決裁権限（運営モデル3章）：お金がかかること・新しい契約・元に戻せない削除は実行せず、承認依頼（レベルB）にする。
- 捏造しない。数字には出典を付ける。権限が無いデータは「未取得」と書く。
- **公開リポジトリ。書かないもの：APIキー・トークン・パスワード、購読者や問い合わせ者のメールアドレス・氏名・問い合わせ内容、社長の氏名・住所・口座、ASPの管理画面の画面写真やアカウントID、ASPとの個別の条件（特別単価など未公開の契約条件）。金額は、月の合計とASPごとの発生・確定の合計までは書いてよい（個別の取引・単価・未公開の条件は書かない）。受信箱にこれらがあれば写さない。**
- 社長のMacへの写しは、社長室の定期タスク（毎朝3:13）がこのフォルダを読んで行う。Mac側で独自に足したファイルは消さない。
- 毎晩のcommitとpushは3:00までに終える（3:13の写しに間に合わせるため）。5:30〜7:30は、日次ジョブ（6:00）と重なるのでpushしない。
- gitで日本語のパスを扱うときは、`git -c core.quotepath=false …`を使う（そのままだと`\345…`の形で表示され、機械的な確認がすり抜ける）。
