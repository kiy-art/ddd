# 部署ごとのナレッジと会議の仕組み（2026-10-10、社長の方針）

部署ごとにナレッジを貯める。ふだんは**部単位**で活動し、部署をまたぐ意見交換は**代表者会議（全部署会議）だけ**で行う。
理由は**意見の偏りを防ぐため**。先に出た意見や強い意見に全体が引っぱられないよう、各部署が先に自分の意見を固めてから持ち寄る。

## 日程
- **部内検討**：毎晩24時（定期タスク「PAR 部内検討(毎日)・全部署会議(水・土)」、日本時間0:00に起動）。
- **全部署会議**：毎週水曜・土曜の夜。部内検討のあとに続けて行い、終わったら社長報告。日本時間で木曜・日曜の0:00に動く回が該当する（曜日は前日の曜日で判定する）。
- 月曜の週次経営会議は廃止（水・土に置きかえ）。

## 構成
- `00_代表者会議/`：進め方・偏りチェック表（`README.md`）、`議題/`、`議事録/YYYY-MM/`、`_テンプレート/`
- 部署フォルダ：`01_全体統括`（議長）、`02_営業`、`03_マーケティング`、`04_SE`、`05_人事`、`06_経理`、`07_経営企画`、`08_Webデザイン`、`09_総務`、`10_監査`（立ち会い。賛否は言わない）
- 各部署フォルダ：`README.md`（役割・KPI）、`knowledge.md`（1行1件）、`01_部内検討/`、`02_会議提出/`（意見書）
- 部署は全事業共通（001_Par.Golf、今後の002、003…）。ナレッジの行には事業番号を付ける。

## 流れ
1. **毎日の部内検討**：各部署が、他部署を見ずに自分のフォルダで検討し、`01_部内検討/YYYY-MM-DD_件名.md`に記録し、学びを`knowledge.md`に追記する。議題も気づきもない部署は「検討事項なし」と1行だけ返して終える（利用枠の節約）。KPIの記録（`backend/scripts/kpi_snapshot.py`）は全体統括が最初に行い、各部署はその台帳を事実として読む。
2. **水・土は続けて全部署会議**（`00_代表者会議/README.md`）：
   - 各部署が意見書を`02_会議提出/`に出す。出したあとは書き換えない（考えが変わったら「会議後」欄に追記）。
   - 議長（全体統括）は、全部署の意見書がそろってから一度に並べる。
   - 発言順は前回からひとつずらす。全体統括は自分の案を最後に出す。
   - 少数意見・反対意見は、理由つきで議事録に残す。
   - 監査は賛否を言わず、偏りチェックだけを行う。
   - 議事録は`00_代表者会議/議事録/YYYY-MM/YYYY-MM-DD_議題名.md`。
   - 各部署は結論を自分の`knowledge.md`の「代表者会議から持ち帰ったこと」に書く。
3. **社長報告**：Notionの報告（Code → 社長室）に、判断が必要なことと報告のみを分けて書く（`docs/report_format.md`）。判断が必要な件は判断ボードへ。「部署別の意見」には各部署の意見書の要点を、「社内の意見（まとめ）」には議事録の結論を入れる。

## 偏りを防ぐ決まり（全部署共通）
1. 部内検討のあいだは、他部署のフォルダを読まない。読んでよいのは事実のデータ（`docs/knowledge/`の台帳・`market.md`・`learnings.md`、`docs/knowledge/kpi/`）と過去の議事録（`00_代表者会議/議事録/`、`docs/meetings/`）だけ。
2. 自分のフォルダにだけ書く。
3. 意見書は会議前に出し、出したあとは書き換えない。
4. 発言順は毎回ずらす。全体統括は自分の案を最後に出す。
5. 少数意見・反対意見は消さない。
6. 監査が偏りをチェックする。
7. 他部署の学びは、代表者会議の議事録を通してだけ取り込む。

## 変わらないこと
- 決裁権限（運営モデル3章）：お金がかかること・新しい契約・元に戻せない削除は実行せず、承認依頼（レベルB）にする。
- 捏造しない。数字には出典を付ける。権限が無いデータは「未取得」と書く。
- **公開リポジトリ**なので、秘密情報・個人情報・未公開の契約条件・金額の詳細は書かない。
- 社長のMacへの写しは、社長室の定期タスク（毎朝3:13）がこのフォルダを読んで行う。Mac側で独自に足したファイルは消さない。
