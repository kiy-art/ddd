## 2. どのキーで束ねるか
キー = (ブランド, カテゴリ, ライン名, 型, ロフト, 長さ, 世代/年, 本数, 左右, レディース, まとめ買い)

1. **ライン名**:`MODEL_LINES` という許可リスト。1行=(ブランド, カテゴリ, 正式名, 一致する正規表現, 一致してはいけない正規表現)。
   - 最初の6行:Spider ZT(5K を除外)、ZXi5、ZXi7、ZX4 Mk II(Mk IIが無ければ別ライン「ZX4」=初代)、ZX5 Mk II、ZX7 Mk II(いずれも ZXi を除外)。
   - 2ラインにまたがる名前、表に無い名前は「キー無し」。キー無しは何があっても束ねない。
2. **型**(パター):max / long / counterbalance / 中尺 / single line / black / standard を別々の軸にして、見つかった集合をキーに入れる。standard 表記も無く他の型も無ければキー無し(「Spider ZT Putter」1行=id921は束ねない)。
3. **ロフト・長さ**:「ロフト3.5度」「36インチ」が名前にあればキーに入れる(あるものと無いものは別キー)。
4. **世代/年**:Mk II の有無でラインを分け、2023などの年は書いてあればキー。「年あり」と「年なし」は同じ発売かを証明できないので束ねない(下の4章の残件)。
5. **アイアン本数**:`iron_sets.set_size` が1つに決まり、単品・選択式でないものだけ。5本と6本は別キー。
6. **シャフト名**はキーに入れない(=TOUR 105/neo/VENTUS/KBS/Diamana/純正違いは同じ商品)。

## 4. 誤統合を防ぐ条件(1枚と5枚、左右、シャフト)
| 誤統合の型 | 防ぎ方 | 残る穴 |
|---|---|---|
| 1枚/5枚/ダース(グローブ・ボール) | 今回の表はパターとアイアンだけ。`bulk`(まとめ買い・N枚・Nダース・N個セット)をキーに入れてあるが、ボール・グローブはライン表に未登録=束ねない | ボールを足すときは、title_cleanerが「ダース」「球」を消すため、**整形前の名前が無いと本数が分からない**(下の穴) |
| 1本/5本/6本(アイアン) | iron_sets の set_size をキーに。単品・選択式・クラブセットはキー無し | 本数の書かれていない名前はキー無し(束ねない) |
| 左右・レディース | 名前に LH/レフト/左/lefty、lady/レディ/ウィメンズ があればキーに入れる | **title_cleanerが「左利き用/レフティ/レディース/メンズ」を既に消している**ため、整形後の名前からは左右が分からないものがある。→ 適用前に、グループ内の価格差と、店のURL・ID(Yahoo!・楽天の商品コード)の目視で確認する運用が要る。生の商品名は保存されていない(Productに列なし) |
| シャフト違い | キーから外す(同一視)。ただしシャフトで価格が違う(ZXi5:¥171,600と¥178,200)ので、統合後に出る価格は最安の1つ=「そのシャフトの価格」になる | 表示を「¥171,600〜」にするなどの文言変更は別議題(景表法上、最安の断定は避ける) |
| 年・世代 | Mk II の有無でラインを分け、年は書いてあればキー | 「2023 ZX4 Mk II」と「年なしのZX4 Mk II」は別グループのまま残る(安全側。束ねたい場合は人が決める) |
| ロフト・長さ | 書いてあればキー | 書いていないものと書いてあるものは別キー(安全側) |
| 別モデルの混入 | 許可リスト方式(表に無いものは束ねない)。ZXi と ZX、Spider ZT と 5K-ZT は除外条件で分離 | 表の1行ごとに正規表現のレビューが要る |

## 5. 適用(統合して本番DBに書く)をなぜ今夜作らないか
1. **戻せない**:既存の `run_title_cleanup_migration` は負け側の行を `db.delete` する(title_migration.py 220行付近)。削除は決裁レベルB。戻す設計なしに同じ方式を流用しない。
2. **URL(slug)の転送が無い**:負け側の /products/<slug> は404になる。リダイレクト機構はリポジトリに無い(next.config.ts の redirects は管理画面用のみ)。検索に出ている行がどれかはSearch Consoleのページ別表示で見る必要があり、存続側を表示の多い行にする入力(`impressions` 引数)だけ用意した。11/11の会議でも「slug+301は11/18以降」とされていた。
3. **価格履歴が混ざる**:負け側の PriceHistory を存続側へ付け替える方式だと、別シャフトの価格が1本の履歴に交互に入り、`/deals` の値下がり%や買い時スコアが偽の下落を出す恐れ(推測、未検証)。
4. **メール通知(PriceAlert)の付け替え**で、購読者が別シャフトの価格を基準に通知される。

### 戻し方(適用案を作るときの設計。今夜は実装しない)
- 削除しない:負け側は `pending_review=True`(=公開から外す。crud.py の公開一覧は pending_review でフィルタ済み)にし、存続側に `merged_into_id`(NULL可の新列)を書く。`scripts/init_db.py` の ALTER 方式で足せる。
- 適用前に「行ごとのスナップショット」(id・slug・name・価格・pending_review)を保存し、戻すときは `pending_review` と `merged_into_id` を元に戻す1回の更新で済ませる(PriceHistory/PriceAlert は付け替えない=履歴が混ざらない)。
- 適用はグループ単位で1つずつ(最初はSpider ZT standard 1グループだけ)、適用前後でサイトの商品数・sitemap(商品=公開数)・/products/<slug> が200かを確認。
- 本番には管理API経由のみ(safe-db-migration の手順:dry-run→監査→適用→報告)。
