## 議題1：段階目標の現実度とクリック計測の置き方
- 推す案：条件付き賛成。(a) SEの目標は「ログレベル error の週（月曜始まり）合計」と定義し、水準を「週20件以下」へ引き下げる。(b) クリック基準値は、分母（PV）が確定するまで件数で暫定記録する。10月末60・12月末400・3月末2,400の見直し可否は、SEは判断材料を持たないため営業・経営企画に委ねる。
- 理由：直近7日の error は7、warning は253で、現行の「週1,000件以下」は約140倍の余裕があり目標として機能しない（根拠: 議題の各部署の進み、`knowledge.md` 2026-10-14 [001]）。定義が3通りある状態では成功率やエラー件数をKPIとして比べられない。warning 253 の主因は日次ジョブのスキップ（楽天・Yahoo!）かもしれないが内訳は未取得（推測）。計測面では、GA4 1日21PV・SC 3日でクリック1（議題の事実）と標本が小さく、PVの分母は当面不安定。
- 見込み効果：直接の収益効果はない。控えめ＝0円、標準＝0円。目標が機能することで異常の早期発見につながる（効果は推測）。月1万円の利益との距離には影響しない。
- 費用・リスク：0円。目標値の変更は社長承認が必要（議題の記載）。error を20件にすると、一時的な外部APIの揺れで未達に見える恐れがある。warning は別枠で監視する。
- 決裁レベル：B（goal・target の変更は社長承認）。定義の明文化だけなら A。
- 過去の試行：無し（`experiments.csv` に目標定義の施策は無い）。
- 市場・時期：感謝祭（10/16〜19）と楽天マラソン（10/14〜17、次10/24〜27）の前に、日次ジョブの異常を拾える状態にしたい。
- 測り方：毎週月曜に管理APIの直近7日 error 件数を記録し、4週連続で比べる。定義変更前後で同じ集計式を使う。

## 議題2：感謝祭・楽天マラソン前の反映と記事・導線
- 推す案：反映の順番は「(1)一覧系canonical＋トップJSON-LD（SE）→ (2)総務が指摘した表記の修正（『予測』見出し・『過去最安値圏』バッジ・『定価より』）→ (3)Webデザイン・マーケの新規UI・記事」。新しい表示を足す前に、表記の誤りを先に直す。実装は議長がpush可能になってから。
- 理由：
  - SEのパッチは7ファイル・追加25行・削除0行で、一時コピーで `git apply --check`・`tsc`・`eslint` が通った（`01_部内検討/2026-10-14_一覧系canonicalとトップJSON-LD.md`）。戻しは git revert、本番データに触れず、日次ジョブ（6:00）と無関係。
  - 依頼の「8ページ」のうち `/about` はリポジトリに無く、実質7ページ（`frontend/app` の一覧）。
  - 注意：`/ranking?category=x` を `/ranking` に寄せるとカテゴリ別ビューは単独で登録されにくくなる。気になるなら ranking だけ外す。
  - 効果は重複URL（トップの `/?buy_score=…` 4種など）の統合が目的で、流入増の保証はない。効果は小〜中（推測、Googleは自動でcanonicalを選ぶ）。
  - 10/12・10/13分が未反映のため、感謝祭に間に合うかは議長の push 可否次第。
  - `/sale/prime-day-2026-10` が本番404（議題の事実）。サイトマップや内部リンクに残っていないか、反映時に確認する（未確認）。

## 議題3：比較ページ629件の扱い
- 推す案：案A（サイトマップから外す・絞る）を先に採用し、案Cの測定を並行して行う。案B（noindex）はGSCの数字が取れてから判断。
- 理由：
  - `app/sitemap.ts` の pairEntries が、全商品×近い価格帯の2商品の組を全部入れている（10/5の453件から約9日で約176件増、議題の事実）。商品名に日時が混入している例を確認済み（`knowledge.md` 2026-10-11 [001]）。
  - 案Aは1か所・数行・約1時間（調べる15分・作る15分・テスト15分・本番確認15分、±30%）。ページ自体は残り、戻せる。効果は「検出・未登録の増加を止める」程度（推測）。
  - 案Bは `compare/[pair]/page.tsx` の generateMetadata に条件付きの `robots: { index:false, follow:true }` を入れる（書き方は `category/[category]/[brand]/page.tsx` 75行と同じ）。約2〜3時間（±40%）。登録済みのページが検索から消えるため、戻しにくい場面がある。
  - 判断材料が足りない。比較ページ経由の表示・クリックは未取得、GSCの「クロール済み・未登録」「検出・未登録」の件数も未取得。noindexで失うものが現時点で不明。
  - 根本対策は、商品名の整形（日時混入）をslug生成の前で直すこと。工数は取り込み処理の確認から始めて半日程度（推測）。本番データの slug を触る場合は `safe-db-migration` の手順に従い、日次ジョブ（6:00）と時間が重ならないようにする。
  - 削除・リダイレクトは今回実行しない（議題の記載どおり）。
- 見込み効果：控えめ＝0クリック（サイトマップ整理のみ）、標準＝クロールが商品ページ・記事に寄る（推測、数値化できず）、強気＝質の低い比較ページの登録が減りサイト全体の評価が上がる（推測）。クリック25／30日の現状では、どの案でも月1万円との距離はほぼ変わらない。
- 費用・リスク：0円。案Aのリスクは、現在登録済みの比較ページがサイトマップ経由の再訪を失うこと（影響は未測定）。サイトマップに残す基準は「両商品が公開・価格あり・slugに日付やセール語が無い・商品ページが上位」の案。
- 決裁レベル：案A＝A。案B＝戻しにくいためBを推す（議長の判断）。
- 過去の試行：EXP-003（2商品比較ページを追加、STEP69、2026-10-03）は「実施後4週」で結果は未測定。比較ページの効果を示す実測は無い。`learnings.md` に、サイトマップ840件の54%が比較ページでその74%は未整形の商品名を含む、との記録あり（マーケ）。
- 市場・時期：比較ページは増え続けており、放置すると判断材料が揃う前に件数が膨らむ。サイトマップ側の整理は今のうちが安い。
- 測り方：GSCで比較ページ（URLに `/compare/` を含む）の「表示回数」「クリック数」「クロール済み・未登録」を一度取得し、案A適用の前後2週でサイトマップ送信数と登録数を比べる。
