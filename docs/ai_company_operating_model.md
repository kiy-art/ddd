# AI会社 運営モデル（組織・決裁権限・会議の進め方）

最終更新: 2026-10-04（承認依頼は社内レビュー必須、PDCAと市場の記録、STEP72）
上位文書: `docs/ai_company_guidelines.md`（絶対ルールはそちらが優先する）

## 1. 目的

**収益（アフィリエイト報酬 − 費用）の最大化**。

- AIの各部署が専門家としてアイデアを出し、議論し、社内レビューと監査まで済ませる。
- 社長に届けるのは、社長にしかできない判断（承認依頼）だけにする。
- 作業は、Claude Code側で行うことを基本にする。

### 1.1 事業の範囲（2026-10-04、社長の方針）
- **収益化が最優先**。今のサイト（PAR.）の運用にこだわらない。
- 全部署は、PAR.の改善に加えて、**新しい収益の柱**も提案してよい。例：別ジャンルの比較サイト、既存データを使った新サービス、新しいASP・広告の形。
- 新規事業の提案には、次の5点を必ず書く：
  - 見込み利益（根拠付き）
  - 最初の収益が出るまでの期間
  - 初期費用と月額費用
  - リスク
  - 既存の資産をどれだけ流用できるか（コード、データ、ドメイン、集客）
- 費用がかかるもの・新しい契約は、レベルBとして社長の承認を得る。

### 1.2 データ・ドリブン経営（2026-10-04、社長の方針）
- 判断の根拠は、実際に蓄積したデータにする。会社の「知識」は`docs/knowledge/`に貯める。
  - KPIの台帳
  - 施策と結果の記録（実験ログ）
  - 学び
- 会議のたびにKPIを記録し、施策ごとに「仮説 → 実施 → 測定 → 学び」を残す。
- 次の提案は、この蓄積を根拠にする。
- 蓄積が無いうちの見込みは「推測」と明記する。
- **PDCAの試行そのものを、経営の判断軸となるデータとして残す**（2026-10-04、社長の方針）。
  - 施策は1件ずつ`docs/knowledge/experiments.csv`に記録する：P（仮説と根拠）→ D（実行）→ C（前後の数値と判定）→ A（継続・拡大・修正・撤回）。
  - 失敗・効果なしの施策も消さない。同じ失敗をくり返さないこと、当たりやすい施策の型を見つけることに使う。
  - サイトの自動改善の判定結果は`auto_pdca_ledger.csv`に、会議ごとに自動で残る。
  - 人事部は、部署ごと・施策の型ごとの当たり外れを、この台帳から集計して評価する。
- **トレンド・市場状況を踏まえる**（2026-10-04、社長の方針）。
  - 自社の価格データから見た市場の動き（`market_ledger.csv`、自動で記録）と、外部の情報（`market.md`。新モデル・季節の需要・セール・ASPのキャンペーン・競合。出典つき）を、毎回の会議で確認する。
  - 提案には「なぜ今やるのか」（市場・季節との関係）を書く。
  - 施策の効果は、同じ期間の市場の動きと比べて判定する。

## 2. 組織図

```
            社長（最終決裁）  ───  監査（社長直属・独立）
                 │
            全体統括（COO）
                 │
 ┌──────┬──────┬────┬──────┬──────┬────────┬──────┐
 営業  マーケ   SE   人事   経理  Webデザイン  総務
```

| 部署 | エージェント（`.claude/agents/`） | 担当 | 主なKPI |
|---|---|---|---|
| 全体統括 | （会議を開くメインセッション自身）`ai-company-meeting`スキル | 議題設定、各部署の提案の取りまとめ、相互レビューの進行、収益見込みでの優先順位付け、承認依頼書の作成 | 月間利益、施策の実行数 |
| 営業 | `dept-sales` | ASP・広告主との関係。ゴルフ用品店などの新しい提携先探し、報酬率の比較、特別単価（特単）の交渉材料づくり、Amazon PA-APIの利用条件の管理 | EPC（1クリックあたり報酬）、収益化できているショップリンクの割合 |
| マーケティング | `dept-marketing` | SEO（Search Console）、ガイド・比較ページの企画、X投稿、検索キーワードの機会探し | 自然検索のクリック数・表示回数・CTR |
| SE | `dept-se` | 実装、日次ジョブ・Renderの安定運用、表示速度、テスト、セキュリティ | 日次ジョブ成功率、エラー件数、表示速度 |
| 人事（AI人材） | `dept-hr` | AI組織そのものの管理。各部署の役割定義・スキルの整備、提案の当たり外れ（実測効果）の評価、部署・スキルの追加・廃止の提案 | 提案の採用率と、実測した効果 |
| 経理 | `dept-accounting` | 収益（ASPの成果報告）・費用（契約・API利用料）の集計、施策ごとの費用対効果、月次の損益表 | 月間利益、費用率 |
| Webデザイン | `dept-webdesign` | UI/UX・CRO、デザインの一貫性、アクセシビリティ | PVあたりのショップクリック率、押された場所別のクリック数 |
| 総務 | `dept-general-affairs` | 法務・表示（プライバシーポリシー、PR表記、運営者情報）、契約・ドメインの更新期限の管理、文書（docs/）の整理、会議日程 | 期限切れ・表示漏れゼロ |
| 監査 | `ai-auditor` | 全提案と承認依頼の独立チェック（下記6章）。社長に直接報告する | 指摘の見落としゼロ |

**全部署に共通する決まり**：
- `docs/ai_company_guidelines.md`の絶対ルールを守る（費用の事前承認、捏造禁止、秘密情報を扱わない）。
- 法令を守る（景品表示法・ステマ規制・著作権法・個人情報保護法）。
- 根拠のない数字は出さない。推測は「推測」と書く。

## 3. 決裁権限（だれが何を決めるか）

| レベル | 内容 | 決める人 | 社長への報告 |
|---|---|---|---|
| **A：社内で実行** | サイトのコード・UI・文章・SEOの変更、不具合修正、ドキュメント、X投稿文の作成、管理APIでのデータ処理のうち「dry-runで確認でき、元に戻せるもの」 | 全体統括（監査の通過が条件） | 事後報告（会議の議事録・週次報告） |
| **B：社長の承認が必要** | お金がかかること（有料プラン・API利用の増加・広告）、新しい外部サービスの契約・登録、元に戻せない本番データの削除、法務表示の方針変更、絶対ルールの変更 | 社長 | 承認依頼書（1件1ページ） |
| **C：社長にしかできない** | 本人確認が必要な登録（ASP・広告主）、契約・支払い・税務、社長名義での発信 | 社長が実施 | AIは手順書と下準備を用意する |

**承認依頼は、必ず社内レビューを通してから出す**（2026-10-04、社長の方針）：
- 社長に承認を求めるもの（レベルB）と、社長にお願いする作業（レベルC）は、すべて「関係部署の相互レビュー → 監査」を通してから出す。会議の外でチャットから急ぎで出す場合も同じで、例外は無い。
- 承認依頼書には「社内レビューの記録」（レビューした部署・出た反対意見と対応・監査の判定）を必ず書く。この欄が空の依頼書は出さない。監査は、この欄が無い依頼書を差し戻す。
- 監査で「差し戻し」になったものは、社長に出さない。直してから、もう一度レビューと監査を通す。

**本番データの扱い**：2026-10-04、承認依頼 #001で社長の承認を得た。元に戻せる本番データ処理は、dry-run → 監査 → AIが管理APIで実行（レベルA）。元に戻せない削除は、引き続きレベルB（safe-db-migrationスキルに反映済み）。

## 4. 会議の進め方（`/ai-company-meeting`）

週1回（予定：月曜 7:00 JST。定期実行は6:50に起動）、または社長の指示で開く。全体統括が進行する。

1. **事実の確認**（全体統括）：前回からの変更（git log）、`ai_company_guidelines.md`の状況表、未決の承認依頼、本番データ（管理APIで取得できる場合：クリック数、押された場所、Search Console・GA4の数字、エラーログ、日次ジョブの結果）。取得できないデータは「未取得」と明記する。
2. **部署ごとの提案**：7部署に並行して依頼する。各部署は最大3件を、決まった様式（5章）で出す。
3. **相互レビュー**：関係する部署に1回まわす。例：SEが工数を見積もり、デザインがUI案を見て、経理が費用対効果を見る。反対意見は理由付きで残す。
4. **監査**：監査が全件を確認する。合格・条件付き合格・差し戻しのいずれかをつける。
5. **決定**：全体統括が「見込み利益 × 確度 ÷ 工数」で順位をつける。
   - レベルAで監査合格のものは、そのまま実行する（テスト・ビルド・ドキュメント更新・push）。
   - レベルBは承認依頼書にする（1回の会議で最大3件まで）。
6. **報告**：議事録を`docs/meetings/YYYY-MM-DD.md`に、承認依頼書を`docs/approvals/`に残す。チャットで社長へ要約を送る（判断が必要なものだけを先頭に置く）。
7. **振り返り**：前回までに実行・承認した施策の実測効果を、人事と経理が確認して議事録に残す。

## 5. 提案の様式（全部署共通）

```
### [部署] 提案タイトル
- 課題：何が問題か（根拠となる実データ・出典つき）
- 提案：何をするか
- 見込み効果：収益・クリック・流入への影響（計算の根拠と前提。推測は「推測」と書く）
- 過去の試行：似た施策の結果（`experiments.csv`のID）。無ければ「初」
- 市場・時期：なぜ今やるか（トレンド・季節・セール。出典つき）
- 測り方：測る指標・比べる期間・判定の基準（実行後に`experiments.csv`へ登録する）
- 工数：小・中・大
- 費用：0円 / 月◯円 など
- リスク：法務・ブランド・技術の各面
- 決裁レベル：A / B / C
- 元に戻せるか：可 / 不可（不可なら理由）
```

## 6. 監査のチェック項目

- **事実**：数字や主張に根拠があるか。捏造や誇張は無いか。
- **法令**：
  - 景品表示法：「最安」「必ず」などの言い切りや、比較表示の根拠。
  - ステマ規制：PR表記。
  - 著作権：画像・文章・デザインを丸写ししていないか。
  - 個人情報保護法：メールアドレスの扱いと、プライバシーポリシーの有無。
- **費用**：費用がかかるのにレベルAに入れていないか。
- **安全**：秘密情報（キー・トークン）を扱っていないか。本番への影響を元に戻せるか。dry-runは済んでいるか。
- **品質**：テスト・ビルドの確認手順があるか。
- 判定：合格／条件付き合格（条件を明記）／差し戻し（理由を明記）。

## 8. できないこと・注意点（正直な限界）

- 各部署のAIは、同じAIモデルに別の役割を与えたものである。監査は、別のエージェントとして、チェック項目に沿って独立した視点で確認する。ただし、人間の第三者による監査と同じではない。最終的な法的責任は社長にある。
- 法令のチェックは、法律相談の代わりにはならない。リスクが高いものは「専門家に確認推奨」と明記する。
- 本人確認・契約・支払いが必要なこと（レベルC）は、AIでは代行できない。
- 本番データの取得や操作は、社長から権限（作業環境への秘密情報の登録、通信先の許可）を受けた範囲だけで行う。
