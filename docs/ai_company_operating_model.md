# AI会社 運営モデル（組織・決裁権限・会議の進め方）

最終更新: 2026-10-04（承認依頼は社内レビュー必須、PDCAと市場の記録、STEP72）
上位文書: `docs/ai_company_guidelines.md`（絶対ルールはそちらが優先する）

## 1. 目的

**収益（アフィリエイト報酬 − 費用）の最大化**。当面の目標は**月1万円の利益**（2026-10-05、社長の方針。手段は問わない）。

- AIの各部署が専門家としてアイデアを出し、議論し、社内レビューと監査まで済ませる。
- 社長に届けるのは、社長にしかできない判断（承認依頼）だけにする。
- 作業は、Claude Code側で行うことを基本にする。

### 1.1 事業の範囲（2026-10-04、社長の方針）
- **収益化が最優先**。今のサイト（PAR.）の運用にこだわらない。
- 全部署は、PAR.の改善に加えて、**新しい収益の柱**も提案してよい。例：別ジャンルの比較サイト、既存データを使った新サービス、新しいASP・広告の形。
- 新規事業の提案には、次の5点を必ず書く：
  - 見込み利益（根拠付き）
  - 最初の収益が出るまでの期間
  - 初期費用と月額費用
  - リスク
  - 既存の資産をどれだけ流用できるか（コード、データ、ドメイン、集客）
- 費用がかかるもの・新しい契約は、レベルBとして社長の承認を得る。

### 1.2 データ・ドリブン経営（2026-10-04、社長の方針）
- 判断の根拠は、実際に蓄積したデータにする。会社の「知識」は`docs/knowledge/`に貯める。
  - KPIの台帳
  - 施策と結果の記録（実験ログ）
  - 学び
- 会議のたびにKPIを記録し、施策ごとに「仮説 → 実施 → 測定 → 学び」を残す。
- 次の提案は、この蓄積を根拠にする。
- 蓄積が無いうちの見込みは「推測」と明記する。
- **PDCAの試行そのものを、経営の判断軸となるデータとして残す**（2026-10-04、社長の方針）。
  - 施策は1件ずつ`docs/knowledge/experiments.csv`に記録する：P（仮説と根拠）→ D（実行）→ C（前後の数値と判定）→ A（継続・拡大・修正・撤回）。
  - 失敗・効果なしの施策も消さない。同じ失敗をくり返さないこと、当たりやすい施策の型を見つけることに使う。
  - サイトの自動改善の判定結果は`auto_pdca_ledger.csv`に、会議ごとに自動で残る。
  - 人事部は、部署ごと・施策の型ごとの当たり外れを、この台帳から集計して評価する。
- **トレンド・市場状況を踏まえる**（2026-10-04、社長の方針）。
  - 自社の価格データから見た市場の動き（`market_ledger.csv`、自動で記録）と、外部の情報（`market.md`。新モデル・季節の需要・セール・ASPのキャンペーン・競合。出典つき）を、毎回の会議で確認する。
  - 提案には「なぜ今やるのか」（市場・季節との関係）を書く。
  - 施策の効果は、同じ期間の市場の動きと比べて判定する。

| 監査 | `ai-auditor` | 全提案と承認依頼の独立チェック（下記6章）。社長に直接報告する | 指摘の見落としゼロ |

**部署のフォルダ**（2026-10-10、社長の方針）：各部署は`docs/departments/<番号_部署名>/`にナレッジ（`knowledge.md`）・部内検討の記録・会議の意見書を貯める。ふだんは部単位で活動し、部署をまたぐ意見交換は代表者会議（全部署会議）だけで行う（4章）。部署は全事業共通。仕組みは`docs/departments/README.md`。

**全部署に共通する決まり**：
- `docs/ai_company_guidelines.md`の絶対ルールを守る（費用の事前承認、捏造禁止、秘密情報を扱わない）。
- 法令を守る（景品表示法・ステマ規制・著作権法・個人情報保護法）。
- 根拠のない数字は出さない。推測は「推測」と書く。

## 3. 決裁権限（だれが何を決めるか）

| レベル | 内容 | 決める人 | 社長への報告 |
|---|---|---|---|
| **A：社内で実行** | サイトのコード・UI・文章・SEOの変更、不具合修正、ドキュメント、X投稿文の作成、管理APIでのデータ処理のうち「dry-runで確認でき、元に戻せるもの」 | 全体統括（監査の通過が条件） | 事後報告（会議の議事録・水土の社長報告） |
| **B：社長の承認が必要** | お金がかかること（有料プラン・API利用の増加・広告）、新しい外部サービスの契約・登録、元に戻せない本番データの削除、法務表示の方針変更、絶対ルールの変更 | 社長 | 承認依頼書（1件1ページ） |
| **C：社長にしかできない** | 本人確認が必要な登録（ASP・広告主）、契約・支払い・税務、社長名義での発信 | 社長が実施 | AIは手順書と下準備を用意する |

### 3.1 お金をかける提案には、投資対効果を必ず示す（2026-10-04、社長の方針）
「これが使えます」だけでは、なんのためにお金を払うのかがわからない。**投資すると、どんな効果がどれだけ出るのか**を示す。

- **少額の基準**（AIが置いた初期値。社長が変えてよい）：月額500円未満、かつ年間6,000円未満、かつ解約がいつでもできるもの。
  - 基準内のもの：承認依頼書に「目的と期待する効果」を1行書けばよい。
  - 基準を超えるもの：経営企画部（`dept-strategy`）が、下の様式で評価書を作り、経理がレビューする。
- **評価書の様式**（承認依頼書の「投資対効果」の欄）：
  1. 何のための投資か：守る効果／増える効果／減る費用／選択肢を残す価値。
  2. 投資しない場合に起きること（比較の基準）。
  3. 効果の見込み：控えめ・標準・強気の3つ。それぞれの前提と出典。推測は「推測」と書く。
  4. 損益分岐：費用を回収するのに必要な成約数・クリック数など。
  5. 測る指標と測定日：何を、いつ測って、見込みと比べるか。
  6. 撤退の基準：いつまでに、どの数字に届かなければ、やめる・見直すか。
- 承認された投資は、`docs/knowledge/investments.csv`に登録する。測定日に実績を書き、見込みとのずれを学びとして残す。

**承認依頼は、必ず社内レビューを通してから出す**（2026-10-04、社長の方針）：
- 社長に承認を求めるもの（レベルB）と、社長にお願いする作業（レベルC）は、すべて「関係部署の相互レビュー → 監査」を通してから出す。会議の外でチャットから急ぎで出す場合も同じで、例外は無い。
- 承認依頼書には「社内レビューの記録」（レビューした部署・出た反対意見と対応・監査の判定）を必ず書く。この欄が空の依頼書は出さない。監査は、この欄が無い依頼書を差し戻す。
- 監査で「差し戻し」になったものは、社長に出さない。直してから、もう一度レビューと監査を通す。

**本番データの扱い**：2026-10-04、承認依頼 #001で社長の承認を得た。元に戻せる本番データ処理は、dry-run → 監査 → AIが管理APIで実行（レベルA）。元に戻せない削除は、引き続きレベルB（safe-db-migrationスキルに反映済み）。

## 4. 会議の進め方（`/ai-company-meeting`）（2026-10-10、社長の方針で改定）

**毎晩の部内検討**と、**毎週水曜・土曜の代表者会議（全部署会議）**の2段で進める。月曜の週次経営会議は廃止した。部署をまたぐ意見交換は代表者会議だけで行い、意見の偏りを防ぐ（先に出た意見や強い意見に全体が引っぱられないよう、各部署が先に自分の意見を固めてから持ち寄る）。仕組みの詳細は`docs/departments/README.md`、会議の手順と偏りチェック表は`docs/departments/00_代表者会議/README.md`。

- **日程**：定期タスク「PAR 部内検討(毎日)・全部署会議(水・土)」が日本時間0:00に起動する。水曜・土曜の夜の回（日本時間で木曜・日曜の0:00に動く回。曜日と日付は12時間前で判定する：`TZ=Asia/Tokyo date -d '-12 hours' +%u`が3か6）だけ、部内検討に続けて代表者会議と社長報告を行う。社長の指示があれば臨時に開く。

### 4.1 毎晩の部内検討
1. **受信箱・判断ボード**（全体統括）：Notionの受信箱の未読と、判断ボードの回答済みを読み、記録先に反映する。
2. **事実の記録**（全体統括）：KPIを記録する（`backend/scripts/kpi_snapshot.py`）。前日からの変更（git log）、日次ジョブの結果、エラーログ、未決の承認依頼をまとめる。取得できないデータは「未取得」と書く。
3. **部内検討**（8部署を別のエージェントとして並行に。部署を呼ぶ前にcommitし、返ったあと`git status`で書き込み先を確かめる。監査は8部署が返ったあとに各部署の記録を確かめる）：各部署は、他部署のフォルダを読まずに、事実のデータだけを根拠に検討し、自分のフォルダに記録する（`01_部内検討/`・`knowledge.md`）。議題も気づきも無い部署は「検討事項なし」と1行。
4. **小さな実行**：部内検討で出たレベルAの不具合修正などで急ぐものは、監査を通してから全体統括が実行してよい。部署をまたぐ判断が要るものは、次の代表者会議の議題に回す。

### 4.2 水曜・土曜の代表者会議（全部署会議）
1. **議題の確定**（議長＝全体統括）：最大3件。事実だけで書く。
2. **意見書**（各部署、並行）：会議の前に`02_会議提出/YYYY-MM-DD_代表者会議.md`に出し、そろった時点でcommitする。出したあとは書き換えない。
3. **一度に並べる**：全部署の意見書がそろってから、議長が発言順のとおりに一度に並べる。発言順は前回からひとつずらす。全体統括は自分の案を最後に出す。
4. **質疑は1回**：反論・修正は意見書の「会議後」欄に追記する。
5. **偏りチェック**（監査）：賛否は言わず、チェック表（全部署が事前に提出したか・書き換えが無いか・同じ根拠だけに頼っていないか・反対0件の理由・まとめが多数意見だけになっていないか・数字の出典・発言順・各意見書の「見たもの」と部内検討の書き込み先の8項目）を記入する。承認依頼とレベルAの実行前のチェック（6章）は、これまでどおり行う。
6. **決定**（全体統括）：「見込み利益 × 確度 ÷ 工数」で順位をつける。少数意見・反対意見は理由つきで残す。
   - レベルAかつ監査合格：実行する（テスト・ビルド・ドキュメント更新・push）。
   - レベルB：承認依頼書（7章）と判断ボード。判断ボードの「部署別の意見」には各部署の意見書の要点を、「社内の意見（まとめ）」には議事録の結論を入れる。
   - レベルC：作業ボードに手順書つきで置く。
7. **議事録**：`docs/departments/00_代表者会議/議事録/YYYY-MM/YYYY-MM-DD.md`（1回の会議で1ファイル、議題は節）。各部署は翌晩の部内検討で、結論を自分の`knowledge.md`の「代表者会議から持ち帰ったこと」に書く。
8. **社長報告**：Notionの報告（Code → 社長室）に、判断が必要なことと報告のみを分けて書く（`docs/report_format.md`）。
9. **振り返り**：測定期間が過ぎた施策の実測効果を、人事と経理が確認して議事録に残す（`experiments.csv`・`proposals.csv`）。

## 5. 提案の様式（全部署共通）

```
### [部署] 提案タイトル
- 課題：何が問題か（根拠となる実データ・出典つき）
- 提案：何をするか
- 見込み効果：収益・クリック・流入への影響（計算の根拠と前提。推測は「推測」と書く）。**円/月に直して書く**（控えめ／標準／強気）。実際のEPCが取れるまでの仮の値（推測）：物販の1クリック 1円／6円／20円、案件枠の1クリック 20円／100円／270円（経理、2026-10-05）
- 過去の試行：似た施策の結果（`experiments.csv`のID）。無ければ「初」
- 市場・時期：なぜ今やるか（トレンド・季節・セール。出典つき）
- 測り方：測る指標・比べる期間・判定の基準（実行後に`experiments.csv`へ登録する）
- 工数：小・中・大
- 費用：0円 / 月◯円 など
- リスク：法務・ブランド・技術の各面
- 決裁レベル：A / B / C
- 元に戻せるか：可 / 不可（不可なら理由）
```

## 6. 監査のチェック項目

- **事実**：数字や主張に根拠があるか。捏造や誇張は無いか。
- **法令**：
  - 景品表示法：「最安」「必ず」などの言い切りや、比較表示の根拠。
  - ステマ規制：PR表記。
  - 著作権：画像・文章・デザインを丸写ししていないか。
  - 個人情報保護法：メールアドレスの扱いと、プライバシーポリシーの有無。
- **費用**：費用がかかるのにレベルAに入れていないか。
- **安全**：秘密情報（キー・トークン）を扱っていないか。本番への影響を元に戻せるか。dry-runは済んでいるか。
- **品質**：テスト・ビルドの確認手順があるか。
- **社内レビュー**：承認依頼書に「社内レビューの記録」（レビューした部署・反対意見と対応）があるか。
- **投資対効果**：少額の基準（3.1）を超える費用に、評価書（見込み・損益分岐・測定日・撤退の基準）があるか。
- 判定：合格／条件付き合格（条件を明記）／差し戻し（理由を明記）。

## 8. できないこと・注意点（正直な限界）

- 各部署のAIは、同じAIモデルに別の役割を与えたものである。監査は、別のエージェントとして、チェック項目に沿って独立した視点で確認する。ただし、人間の第三者による監査と同じではない。最終的な法的責任は社長にある。
- 法令のチェックは、法律相談の代わりにはならない。リスクが高いものは「専門家に確認推奨」と明記する。
- 本人確認・契約・支払いが必要なこと（レベルC）は、AIでは代行できない。
- 本番データの取得や操作は、社長から権限（作業環境への秘密情報の登録、通信先の許可）を受けた範囲だけで行う。
