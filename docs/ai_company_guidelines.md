## 2. 事業戦略（決定事項）

- **ターゲット層**：欲しいクラブが決まっている中級者（例：「〇〇 いつ下がる？」と検索する層）。
- **価格データ取得**：Keepaなどの有料APIは使わず、Amazon・楽天・Yahoo!の無料APIを利用する。
- **お買い得判定（過渡期の方針）**：過去データが十分蓄積するまでは、
  - 「定価（MSRP）からの割引率」
  - 「発売日からの経過日数（モデルチェンジサイクルの推測）」
  を使って「今が買い時」かを判定する。
- **収益化**：まずはアフィリエイト（Amazon・楽天・Yahoo!）のみに集中する。

## 3. 現在のシステム構造（調査結果）

### 3.1 技術スタック

- **バックエンド**: FastAPI + SQLAlchemy（本番: Postgres on Render / ローカル: SQLite）
- **フロントエンド**: Next.js（App Router）+ Tailwind CSS v4
- **AI文章生成**: Anthropic Claude API（`app/ai.py`）— 事実の分析結果をもとに紹介文を生成するだけで、買い時判定そのものはルールベース（後述）
- **デプロイ**: Render（`golf-deals-backend` / `golf-deals-frontend`、`render.yaml`で定義）
- **日次バッチ**: GitHub Actions（`.github/workflows/update-prices.yml`）→ `POST /api/admin/fetch-rakuten` を1日1回叩く
  - **重要な訂正（2026-09-22）**：「Renderの無料Cron」という表現が過去の指示に出てきたことがあるが、**Renderの公式Cron Jobsサービスは無料ではない**（1ジョブあたり月額最低$1〜の従量課金、無料プランの対象外）。実際に無料で動いているのはRenderのCronではなく、**GitHub Actionsのスケジュール実行（`schedule: cron`）から、無料のRender Web Service（`golf-deals-backend`）のHTTPエンドポイントを1日1回叩く**という構成。今後「Renderの無料Cron」という指示が来た場合は、このGitHub Actions方式を指すものとして扱う（Renderの有料Cron Jobsサービスは絶対ルール1により無断では契約しない）。

### 3.2 データ取得・保存パイプライン

1. **価格取得**（`app/rakuten.py`, `app/yahoo.py`）
   - 楽天市場「商品検索API」: メインの価格ソース。キーワード検索結果の中央値に最も近い価格を採用（外れ値の誤マッチを避けるため、最安値ではなく中央値ベースで選ぶ）。
   - Yahoo!ショッピング「商品検索API」（本セッションで追加）: 独立した第2の価格ソース。`yahoo_price`という別カラムに保存され、`current_price`や`buy_score`など楽天ベースの分析には一切影響しない設計。
   - 両方とも、価格が異常値（参考価格の0.5〜2.0倍の範囲外）またはアクセサリ/パーツらしき商品名の場合は自動反映せず、`ErrorLog`に記録してスキップする。
2. **保存**（`app/crud.py`）: `PriceHistory`テーブルに追記。`current_price`/`average_price`（30日平均）/`lowest_price`（全期間最安）/`price_change_percent`を再計算。
3. **買い時判定**（`app/analysis.py`）: ルールベースのスコア（`buy_score`: strong_buy/buy/neutral/not_buy/insufficient_data）と0-99の`buy_signal_score`を算出。**AIは一切関与しない**（同じ入力からは常に同じ結果）。
4. **価格予測**（`app/forecast.py`）: 商品自身の価格履歴に対する線形トレンド予測。信頼度（high/medium/low）はデータ量・期間で決まる。発売から60日未満の商品は信頼度を強制的にlowにする（発売直後価格は定価付近に固定されがちなため）。
5. **AI文章生成**（`app/ai.py`）: 上記の事実が変化した場合のみClaude APIを呼び出す（`content_hash`による差分検知でコスト制御）。`insufficient_data`の商品やAPIキー未設定時は生成しない。
6. **新商品の自動発見**（`app/discovery.py`）: 楽天のカテゴリ検索から新商品候補を発見し、`pending_review=True`で作成。**管理者が承認するまで一般公開されない**（誤マッチ・中古品混入を防ぐため）。

### 3.2.1 日次ジョブの堅牢化（2026-09-22）

`POST /admin/fetch-rakuten`は1リクエストの中で「楽天価格取得→Yahoo価格取得→新商品発見→人気ランキング同期→全商品の買い時再分析→値下がり通知メール送信」を順に実行する、実質的に日次バッチ処理そのもの。以下の対策で、**どこか1ステップが予期せぬ例外を出しても、それ以降のステップ（特に最後に実行される値下がり通知メール）が止まらないようにした**：

- 各ステップを個別の`try/except`で囲み、失敗した場合は`db.rollback()`してから次のステップへ進む（`db.rollback()`が無いと、Postgres環境では失敗後のセッションで以降のクエリが全て失敗する — 実際に踏みかねなかった不具合）。
- 商品ごとの再分析ループも1商品の失敗で全体が止まらないよう個別に保護（従来ルーターにはこの保護が無かった。`scripts/update_prices.py`側には元々あったので、両者を揃えた）。
- ジョブの最後に必ず`ErrorLog`（`source="daily_job"`, `level="info"`）へ実行結果サマリーを1件書き込む。`/admin/logs`は新しい順に並ぶため、日次ジョブが最後まで到達したかどうかを管理画面で一目で確認できる（GitHub Actionsのログを見に行かなくてよい）。
- `.github/workflows/update-prices.yml`側も強化：
  - Renderの無料Webサービスは15分アイドルでスリープするため、本処理の前に軽いヘルスチェックで先に起こす（`continue-on-error: true`、失敗しても本処理に影響しない）。
  - `curl --max-time`を180秒→900秒に延長（商品数が増えるほど各API呼び出し間隔（約1.1秒/件）の積み重ねで所要時間が伸びるため）。
  - `--retry 1 --retry-delay 60 --retry-all-errors`でネットワーク瞬断やRenderの再起動に対して1回だけ自動リトライ（パイプラインは冪等に近い設計＝2回走っても致命的な不整合は起きない）。
  - ジョブ全体に`timeout-minutes: 35`（リトライ込みの最悪ケースを想定）。
  - 実行結果をGitHub ActionsのStep Summaryにも出力（失敗時も出す）。スケジュール実行が失敗した場合はGitHubがリポジトリオーナーに自動でメール通知する（追加設定不要）。
- 検証：`backend/tests/test_api.py::test_fetch_rakuten_survives_a_step_blowing_up`で、新商品発見ステップが例外を投げても値下がり通知ステップまで実行されることを確認済み。

### 3.3 「ANALYZING」問題と現状のフォールバック処理

- フロントエンドの`AiBuySignal.tsx`は、`buy_score === "insufficient_data"` または `history_span_days < 7日` の場合、スコアゲージを「フォールバック表示」に切り替える（**解決済み・2026-09-22**）。
  - MSRP（定価）がある場合：`lib/fallbackScore.ts`が定価割引率＋発売経過日数から代替スコアを算出し、破線リングの「定価比較」として表示（実データに基づく本来のスコアとは視覚的に区別）。
  - MSRPが無くても発売日または`is_current_generation`（型落ち確認フラグ）がある場合：`lib/modelCycle.ts`がゴルフのモデルチェンジ周期（約1〜2年）に基づく推測メッセージ（「型落ち間近」「底値圏の可能性」等）を生成し、商品詳細ページの「今買うべき？」欄・「いつ安くなりそう？」欄に表示。`is_current_generation===false`という確認済み事実がある場合はFACTタグ、発売日のみからの推測はAI推測タグで明確に区別。
  - 何も無い最後の場合のみ、ラベルを「ANALYZING」から「NEW LISTING」に変更（グレーのリングは維持）。
  - `history_span_days === 0`のときに「0日分」と表示していた箇所（`ProductCard.tsx`/商品詳細ページ/`compare/page.tsx`）はすべて「登録されたばかりの商品です」等の文言に変更済み。
- この「7日」という閾値（`THIN_DATA_DAYS`）は **8箇所**（`ProductCard.tsx`、商品詳細ページ、`AiBuySignal.tsx`、`lib/badges.ts`、`app/page.tsx`、`app/popular/page.tsx`、`app/compare/page.tsx`、`app/products/[slug]/opengraph-image.tsx`）に同じ値がハードコードされている（2026-09-22時点、STEP6〜8で増加）。**DRY違反であり、今後閾値を変更する際は8箇所すべて直す必要がある技術的負債（未解消）。** 2026-09-22時点で全箇所`=7`かつ同一の判定式であることは確認済み（ズレは発生していない）。
- 「データ不足」時に架空の数値で埋めることは一切していない（サイト全体の設計原則）。上記フォールバックもすべて実在するフィールド（MSRP・発売日・型落ちフラグ）からの計算であり、価格レンジバー・価格予測・買い時カレンダーなど本当に実データが無いセクションは引き続き明示的に「データ不足」「収集中」と表示する。

### 3.4 将来の別ジャンル展開に向けたコード分離状況（拡張性）

**結論：現状はゴルフ専用に強く結合しており、他ジャンルへの横展開には相応の書き換えが必要。**

- `app/models.py`の`CATEGORIES = ["driver", "iron", "wedge", "putter", "ball"]`が全カテゴリ判定のハードコード起点。
- `app/discovery.py`の`CATEGORY_SEARCH_KEYWORDS`（「ゴルフ ドライバー 新品」等）と`BRAND_KEYWORDS`（PING/Titleist等のゴルフブランド辞書）は完全にゴルフ専用。
- 商品の「ポジショニング」情報（`skill_level`: beginner/all_levels/advanced、`performance_type`: distance/forgiveness/control/balanced）はゴルフクラブ特有の分類軸。
- `SeasonalTrend.tsx`の季節傾向テキストはカテゴリごとにゴルフ業界の一般論をハードコードしたもの。
- サービス名・DB名（`golf-deals-backend`/`golf-deals-frontend`/`golf_deals`）、ブランド名「PAR.」もゴルフに紐づく。
- 一方で、**価格追跡・買い時判定・予測エンジン（`analysis.py`/`forecast.py`/`pipeline.py`）自体はジャンル非依存の汎用ロジック**であり、「商品名・ブランド・カテゴリ・価格履歴」という抽象化されたデータモデルの上に成立している。ここは横展開時の資産になる。

### 3.5.3 sitemap.xmlの堅牢化（STEP10、2026-09-22）

**きっかけ**：Google Search Consoleにsitemap.xmlを送信したところ「27件のエラー」「検出されたページ数: 0」というエラーが発生。

**根本原因（特定結果）**：`app/sitemap.ts`が商品・ブランド一覧をバックエンドAPIから取得する際、取得に失敗すると例外を`try/catch`で握りつぶし、空配列を返していた。Renderの無料プランはアイドル状態からのコールドスタート（数十秒かかることがある）が発生するため、Googlebotがクロールしたタイミングでバックエンドが起動中/応答遅延だった場合、商品・ブランドURLが一切含まれない（静的ページのみの）不完全なsitemap.xmlが生成されていた可能性が高い。さらに`revalidate`指定が無く、毎回のリクエストでバックエンドへの生存確認から始まる作りだったため、遅延・タイムアウトのリスクが常に存在していた。

**対応内容**：
- `export const revalidate = 3600`（1時間ごとのISR）を追加。クロールのたびにバックエンドへ問い合わせる代わりに、生成済みのsitemapをキャッシュから高速に返す（ローカル検証：初回308ms→キャッシュヒット時21ms）。
- 商品・ブランド取得失敗を握りつぶす`try/catch`を廃止。取得に失敗すると例外がそのまま伝播し、Next.jsのISRは直前に生成できた正常なsitemapを配信し続け、次回リクエストで再試行する（`node_modules/next/dist/docs/01-app/02-guides/incremental-static-regeneration.md`に明記された挙動）。空の不完全なsitemapを配信し続ける事態を防ぐ。
- バックエンド呼び出しに8秒のタイムアウトを追加（コールドスタート中の応答待ちでルート全体が長時間ハングするのを防ぐ）。
- 空/未設定のslug・ブランド名を除外し、URL単位の重複除去を追加。
- `next.config.ts`に`trailingSlash: false`を明示（サイト全体の既存の挙動と一致させ、今後の曖昧さを排除）。

**検証結果**：
- `npm run build`・`eslint`：エラーなし。
- 生成したsitemap.xmlをXMLパーサーで構造検証（`urlset`名前空間、絶対URL、priority範囲0-1、changefreq列挙値、lastmod書式、重複`<loc>`の有無）：問題なし。
- バックエンドを意図的に停止した状態でsitemap.xmlにアクセスし、0.19秒でHTTP 500（空の不完全なsitemapを200で返す旧挙動ではなく、明確な失敗として扱われることを確認）。バックエンド復旧後は正常なsitemap.xmlが返ることを確認。

### 3.5.4 X（Twitter）自動投稿機能（STEP11、2026-09-22）

**背景**：フェーズ2（集客と売上発生）の第一弾。Amazonアソシエイト本審査（3.5参照、直近180日で3件以上の適格販売が必要）を最速で通すため、SEOが育つまでの即効性のある集客手段としてXへの自動投稿を追加した。

**実装内容**：
- 新規モジュール`app/x_post.py`。日次バッチ（`/admin/fetch-rakuten`・`scripts/update_prices.py`）の**最後の工程**として実行される（価格更新・AI再生成・価格アラートより後）。手動実行用に`/admin/post-to-x`エンドポイントと、管理画面に「今すぐ投稿」ボタンも追加（他の任意連携＝Yahoo取得・値下がり通知と同じパターン）。
- **商品選定ロジック**（`select_deals_of_the_day`）：3.3で確立した「実データ優先・フォールバックは補完」の二段構成を再利用。
  1. 第一候補：`buy_score`が`strong_buy`/`buy`かつ`buy_signal_score`があり、価格履歴が`RELIABLE_TREND_MIN_HISTORY_DAYS`（7日）以上ある商品（＝フロントの`THIN_DATA_DAYS`と同じ「信頼できる実シグナル」基準）。
  2. 第二候補（1で規定数に満たない場合のみ）：定価（MSRP）からの割引率が大きい順（値上がり・定価不明の商品は対象外）。
  3. どちらの基準も満たす商品が無い日は**何も投稿しない**（存在しない「お得情報」を捏造しない）。
  - `crud.list_products(published_only=True)`は使わない。このゲートは`buy_score == "insufficient_data"`の商品を一覧から除外する仕様（3.3のANALYZING調査で判明した「一覧には出ないが商品ページ自体は生きている」という既知の区別）だが、フォールバック候補としてはまさにこの層を見る必要があるため。

- **文字数管理**：X独自の「加重文字数」（日本語等の非ラテン文字は2文字分としてカウント、URLは実際の長さに関わらず23文字固定）を近似計算し、280文字を超える場合は安全に切り詰めて「…」を付与する。
- **認証方式**：OAuth 1.0a（ユーザーコンテキスト、HMAC-SHA1署名）を採用。無料枠のApp-onlyトークンは投稿権限が無いため、X Developer Portalの「Keys and tokens」で発行するAccess Token/Secret（有効期限なし、アプリのPermissionsを"Read and Write"に設定した上で発行）が必要。SDKは使わず、既存コードの`httpx`直接呼び出しのスタイル（`rakuten.py`/`yahoo.py`/`email.py`）に合わせて自前で署名。
- **安全な組み込み（例外分離）**：投稿処理全体を独自の`try/except`で囲み、失敗時は`db.rollback()`の上で`ErrorLog`に記録するのみで、日次バッチ本体（価格更新・値下がり通知等）には一切影響しない設計（3.2.1で確立したパターンを踏襲）。この分離が実際に機能することをテスト（`test_fetch_rakuten_survives_x_post_blowing_up`）で確認済み。
- **未設定時の挙動**：`X_API_KEY`/`X_API_SECRET`/`X_ACCESS_TOKEN`/`X_ACCESS_TOKEN_SECRET`の4つが揃っていない場合は、エラーにはせず単純に投稿をスキップする（`YAHOO_CLIENT_ID`/`RESEND_API_KEY`と同じ「未設定でも安全に動く」設計）。

**必要な環境変数（Renderに登録が必要）**：
| 変数名 | 内容 |
|---|---|
| `X_API_KEY` | X Developer PortalのApp「Consumer Keys」→ API Key |
| `X_API_SECRET` | 同上 → API Key Secret |
| `X_ACCESS_TOKEN` | 同Appの「Keys and tokens」→ Access Token（Permissionsを"Read and Write"にしてから生成） |
| `X_ACCESS_TOKEN_SECRET` | 同上 → Access Token Secret |

※`ANTHROPIC_API_KEY`（設定済み）は投稿文のAI生成にも流用される。未設定でもルールベース文面で投稿自体は継続する。

### 3.5.5 商品カタログの安全な自動拡張（STEP12、2026-09-22）

**背景**：Amazonアソシエイト本審査（3.5参照）に必要な「直近180日で3件以上の適格販売」を最速で達成するため、購入ハードルが低く回転率の高い消耗品（ゴルフボール等）を中心に商品数を拡大する方針。

**実装内容（`app/discovery.py`）**：
- **検索キーワードの拡張**：`CATEGORY_SEARCH_KEYWORDS`をカテゴリ→単一キーワードからカテゴリ→キーワード一覧に変更。driver/iron/wedge/putterは既存通りカテゴリ自体は既に検索対象済み（新規追加ではなく既存動作の確認）。ゴルフボールのみ、汎用キーワード（「ゴルフボール 1ダース 新品」）に加え、中級者以上が指名買いする定番モデル名（Titleist Pro V1、スリクソン Z-STAR、ブリヂストン TOUR B）を個別キーワードとして追加。汎用検索は無名の安価な詰め合わせに偏りやすいため、モデル名を直接検索することで確実に拾う。
- **1回の検索あたりの取得件数**：Rakuten Ichiba商品検索APIの1リクエストあたり上限（30件）まで引き上げ（旧: 10件）。
- **カテゴリごとの新規追加上限**（`MAX_NEW_PER_CATEGORY`）：3件→20件に引き上げ（カテゴリ内の全キーワード合算）。複数キーワードを持つカテゴリ（ボール）は上限に達した時点で残りのキーワード検索自体をスキップし、Rakuten APIへの無駄なリクエストを避ける。
- **安全な自動公開フィルター（新機能）**：これまで自動検出商品は例外なく`pending_review=True`（承認待ち）だったが、以下の**両方**を満たす商品のみ`pending_review=False`（即時公開）にする（`_is_safe_to_auto_publish`）：
  1. NGワード（`AUTO_PUBLISH_NG_KEYWORDS`：「中古」「ヘッドカバー」「シャフトのみ」「スリーブ」「用」）を商品名に含まない。
  2. 価格が閾値以上：ボールは3,000円以上、クラブ類（driver/iron/wedge/putter）は10,000円以上。
  - この判定は「候補として採用するかどうか」（既存の`_looks_like_accessory`・`MIN_DISCOVERY_PRICE`・ブランド一致判定、変更なし）とは独立した**追加の**判定であり、両方の基準から外れる、または際どい商品は従来通り承認待ちのまま安全側に倒す。
- **表示テキストの修正**：管理画面「商品の自動検出」カードおよび各種完了メッセージが「自動検出された商品は承認するまで公開されない」という、STEP12で実態と食い違うことになった文言だったため、安全な商品は自動公開される旨に修正（実際の挙動と表示文言が食い違う既知の不具合パターン ── 3.5.1のホームページbestBuyバグと同種 ── を未然に防止）。

**安全設計の考え方**：「採用するかどうか」のフィルター（アクセサリ除外・最低価格・ブランド一致）は一切変更していない。今回変更したのは、既に候補として採用された商品のうち「即時公開して良いか、人の確認を待つか」の判定のみ。判定に迷う・際どい商品は必ず安全側（承認待ち）に倒れる設計とした。

**運用上の留意点**：Rakutenの検索結果は日によって大きくは変わらないため、同日中に「今すぐ検出」を複数回クリックしても新規追加件数は伸びにくい（重複除去が効くため）。「数百件規模」への到達は、今回追加したキーワードの幅と引き上げた上限により1回の実行での新規追加数を底上げしつつ、日次自動バッチによる継続的な蓄積（Rakutenの人気ランキング変動・新規出品の反映）を通じて段階的に進む見込み。即座に数百件へ到達することを保証するものではない。

### 3.5.6 管理画面のリアルタイム・ライブダッシュボード（STEP13、2026-09-22）

**背景**：日次バッチ処理（楽天価格取得→新商品探索→人気ランキング同期→買い時判定・AI説明文生成→値下がり通知→SNS投稿）が今どの工程にいるか、管理画面上で視覚的にリアルタイム把握できるようにする要望。

**実装内容**：
- **配信方式**：Server-Sent Events（SSE）を採用。WebSocketsではなくSSEを選んだ理由は、配信方向が「サーバー→ブラウザ」の一方向で十分なため（ブラウザからサーバーへの追加メッセージは不要）、FastAPIの標準機能`StreamingResponse`だけで実装でき、Pusher等の有料/サードパーティ製リアルタイム通信サービスが一切不要なため。
- **新規モジュール`app/progress.py`**：プロセス内（インメモリ）のpub/sub。Renderの無料プランのバックエンドはuvicornワーカー1個のみで動作している（`render.yaml`の`startCommand`に`--workers`指定なし、3.1参照）ため、Redis等の外部ストアなしで「プロセス内の購読者リストにブロードキャストする」だけの単純な実装で足りる。**将来バックエンドを複数ワーカー/複数インスタンスに拡張する場合はこの前提が崩れる**ため、その際はRedis等の外部pub/subへの置き換えが必要になる旨をコード内コメントに明記。
- **配信の粒度**：「ジョブ（例：日次バッチ全体、または個別の「今すぐXX」ボタン1つ）」の中に複数の「ステージ」（市場価格取得中・新商品探索中・人気ランキング同期中・買い時判定AI生成中・値下がり通知送信中・SNS投稿中）があり、各ステージの開始・進捗（件数/全体件数）・完了を逐次配信する。楽天/Yahoo!価格取得・新商品探索・買い時判定の3ステージは実際に処理件数が数百件規模になりうる（STEP12参照）ため、`on_progress`コールバック（オプション引数、既存の呼び出し元には一切影響しない設計）を`pipeline.fetch_rakuten_prices`/`fetch_yahoo_prices`/`discovery.discover_new_products`に追加し、1件ごとに進捗を報告できるようにした。買い時判定ステージは全商品ループが速いため、5件ごとに間引いて配信（無駄なイベント過多を防止）。
- **既存の日次ジョブ（`/admin/fetch-rakuten`）・個別手動実行エンドポイント（`/admin/run-update`、`/admin/fetch-yahoo`、`/admin/send-price-alerts`、`/admin/post-to-x`、`/admin/sync-popularity`、`/admin/discover-products`）すべてに組み込み**：どのボタンを押しても同じライブダッシュボードに反映される。
- **新規エンドポイント`GET /admin/live`**：SSEストリームを配信。接続直後に「現在（または直近に完了した）ジョブの状態」を1件即座に送るため、実行中に開いても空白にならない。15秒ごとにキープアライブコメント行を送信（Renderのプロキシ等がアイドル接続を切断するのを防止）。
- **重要な実装上の注意（認証）**：ブラウザ標準の`EventSource`はカスタムヘッダーを送れないため、このAPIが要求する`Authorization: Bearer <token>`ヘッダー（Cookie未使用、`app/auth.py`）を送信できない。そのため`EventSource`ではなく、`fetch()` + `ReadableStream`を手動でパースする方式をフロントエンドで採用（新規`lib/useLiveJobUpdates.ts`）。ネットワーク切断時は3秒後に自動再接続。

**検証結果**：

### 3.5.7 店舗比較表のバグ修正とコンバージョン最適化（STEP14、2026-09-22）

**きっかけ**：「Yahoo!ショッピングの行が比較表から抜け落ちる」という不具合報告と、「Amazonの文言が消極的」「楽天を推しすぎている（回し者に見える）」というUI公平性の課題。

**原因調査結果（Yahoo!非表示バグ）**：`components/StoreComparisonTable.tsx`・バックエンドのスキーマ（`ProductOut`/`ProductDetailOut`に`yahoo_price`/`yahoo_url`含む）・APIルーター（`GET /api/products/{slug}`）を一通り確認したが、**いずれもコード自体にバグは無かった**。ローカルで実際にDBへYahoo!価格データを投入し、フロントエンドが正しくレンダリングすることを実機（Playwright）で確認済み。つまり「バグ」の実体は、**元々の設計が「そのモールで実際に価格が見つかった場合のみ行を表示し、見つからない場合は行ごと消す」という仕様だった**こと。楽天は`current_price`（商品自体の主価格）が必ずあるため常に表示される一方、Yahoo!は「マッチが見つからない日」や「YAHOO_CLIENT_ID未設定の環境」では行自体が消え、あたかも「取得できているはずなのに表示されない」ように見えていた。これはコードの欠陥というより、**「データが無いなら黙って隠す」という設計判断そのものが、期待される見え方（3社は常に並んで見えるべき）とズレていた**という設計上の問題であり、同時に「楽天ばかり目立つ」というUI公平性の課題とも直接つながっていた（第2・第3のモールが条件次第で消えるため、結果的に楽天だけが常に主役に見える）。

**対応内容**：
- **Yahoo!ショッピングの行を常時表示に変更**：実際の価格が取得できていればその価格とリンクを表示し、取得できていない場合は（Amazonの既存行と同じ考え方で）Yahoo!ショッピングの検索結果ページへの通常リンク（アフィリエイトタグなし・無報酬、`lib/yahoo.ts`新規作成）にフォールバックする。行が条件次第で消えることが無くなった。
- **Amazonのマイクロコピー改善**：ボタン文言を「Amazonで探す →」→「Amazonで最安値をチェック →」に、価格欄横の説明文を「商品名の検索結果ページが開きます」→「Amazon内の価格をチェック（最安値の可能性あり）」に変更。事実として断定できない「最安値かもしれない」という可能性ベースの表現に留め、誇大表示にはしていない。
- **ボタンデザインの差別化（原則ベース）**：「確定価格が分かっている行」（楽天・Yahoo!の実データ）は従来通りの控えめなアウトライン、「価格は不明だが確認する価値がある行」（Amazon・Yahoo!未マッチ時のフォールバック）はブランドカラーの塗りつぶしボタンに変更しクリックを誘発。この差別化は**「特定のモールだから」ではなく「価格が分かっているかどうか」という状態に基づく原則的なルール**にしており、日によってどのモールがどちらの見た目になるかは変わる（例：Yahoo!に実データがあればYahoo!も控えめな表示になる）。メーカー公式サイトの行は「最安値の可能性」という表現が実態と合わない（定価販売が基本）ため、この強調対象からは除外。
- **テーブルの並び順を「価格が安い順」に変更**：従来はコード内の記述順（楽天→Yahoo→公式→Amazon）で常に楽天が先頭だった。実際の価格が判明している行を安い順に並べ、価格不明の行は末尾に回すことで、**その日実際に最安値のモールが自然に先頭へ来る**ようにした。「楽天が常に一番目立つ」という構造的な偏りを解消。
- 分析イベント（`cta_click`の`cta_type`）に、Yahoo!の検索フォールバック用の新しい区分（`marketplace_search`）を追加（従来は誤って`official`扱いになっていた）。

**検証結果**：
- `npm run build`（TypeScript込み）：エラーなし。
- 実機検証（Playwright）：①Yahoo!に実データがある場合に正しく表示され、価格が最安なら「最安」バッジと共に先頭に来ることを確認。②Yahoo!に実データが無い場合、行が消えずに検索リンクへのフォールバックとボタンが表示されることを確認。③デスクトップ幅・モバイル幅の両方でレイアウト崩れが無いことを確認（モバイル時の横スクロール自体は本改修以前からの既存仕様で、今回変更していない）。

### 3.5.8 商品名のクレンジングと重複統合（STEP15、2026-09-22）

**背景**：楽天等のショップが付けた宣伝文句込みの商品名（「【送料無料】〇〇 ポイント10倍!!」等）がそのまま登録され、同じ型番の商品が複数バラバラに登録される問題、および「ふるさと納税」「訳あり」等の非retail商品の混入。

**実装内容**：

1. **強力なNGワードによる完全排除**：`app/pipeline.py`に新設した`NON_RETAIL_LISTING_KEYWORDS`（「ふるさと納税」「ふるさと」「訳あり」）と`_looks_like_non_retail_listing()`を、既存の`_looks_like_accessory()`（ヘッドカバー等）と並列で、商品発見時（discovery.py）・日次価格取得時（pipeline.py、楽天・Yahoo!両方）の両方に組み込んだ。該当する商品は候補にすら一切ならない（承認待ちにもならず、完全に破棄）。
   - **「得」「ポイント」「送料無料」は意図的にこのNGワードに含めなかった**：これらは実在するほぼ全ての楽天/Yahoo!出品（正規のゴルフクラブ含む）のタイトルに付いている宣伝文句であり、これを「登録拒否」の基準にすると通常の商品検索・既存商品の価格マッチングまで機能しなくなる（発見できる商品がほぼゼロになる、既存商品の日次価格更新が軒並み失敗する）重大な副作用がある。指示の意図（「きれいな商品名にする」）を汲み、これらは次項のクレンジング（表示名からの除去）で対応する方針に変更した。
2. **商品名クレンジング（新規`app/title_cleaner.py`）**：
   - 正規表現による決定的な処理（`strip_promotional_noise`）：【】/[]で囲まれた宣伝タグを丸ごと除去、「送料無料」「ポイント◯倍」「期間限定」「新品」「正規品」等の定型的な宣伝フレーズを除去。常に動作し、無料。
   - Claude APIによる追加の精緻化（`clean_product_title`、ANTHROPIC_API_KEY設定時のみ）：正規表現処理後のテキストと、既に判定済みのブランド名・カテゴリのみを渡し、「実際に含まれる文字列の削除のみ、新たな情報の追加は禁止」と厳格に指示。出力は「空でない」「入力より大幅に長くない」「ブランド名を含む」の3点を検証し、いずれか不合格ならAI出力を破棄して正規表現の結果にフォールバック（`app/ai.py`と同じ「AIは創作しない」原則）。
   - `app/discovery.py`に統合：発見した商品は生タイトルではなくクレンジング後の名前でDB登録される。
   - **安全上の注意**：中古/用等のAUTO_PUBLISH_NG_KEYWORDS判定（STEP12）は、クレンジング後ではなく**生タイトル**に対して行う。クレンジングが「中古」等を誤って削ってしまった場合に、中古品が自動公開されてしまう事故を防ぐため。
3. **クリーンな商品名による重複排除・統合**：
   - `discover_new_products`の重複チェックを、生タイトルではなく（ブランド, クレンジング後の名前）のペアで行うよう変更。宣伝文句だけが違う同一商品が、今後は自動的に1つに統合される。
   - **既存DBのクレンジング・統合用の移行スクリプト`backend/scripts/migrate_clean_titles.py`を新規作成**：
     - 全商品の名前をクレンジングし、その結果（ブランド, クレンジング後の名前）が同じになった商品グループを1つに統合する。
     - 統合時：既に公開済み（承認待ちでない）商品を優先して存続させる（承認待ちの重複が誤って「生き残り」になり、公開済み商品が消えることがないように）。次点で価格履歴が多い方、さらに次点で登録が古い方。
     - 価格履歴・値下がり通知アラート・エラーログは、統合される側（負け側）から存続する側へSQLレベルで一括付け替えてから、負け側を削除する（SQLAlchemyのORMリレーション経由の代入ではなく直接UPDATE文を使用 — cascade="all, delete-orphan"の誤動作でデータが消えるのを避けるため）。
     - 手動調査済みの事実（msrp・発売日・スキルレベル等）は、存続側に値が無い場合のみ負け側から補完し、既存の値は上書きしない（`pipeline.fetch_rakuten_prices`の画像/URL補完と同じ「手動キュレーションデータは上書きしない」原則）。
     - 統合後は`crud.recompute_current_price`→`pipeline.sync_product_analysis`の順で呼び出し、結合後の価格履歴全体から現在価格・平均・買い時判定・AI説明文を再計算する。
   - **安全設計**：デフォルトは**dry-run**（何も書き込まず、実行計画を表示するのみ）。実際に反映するには`--apply`が必要。再実行しても安全（既にクレンジング済み・統合済みのものは対象から外れる）。

**検証結果**：
- バックエンド新規テスト：`tests/test_title_cleaner.py`（11件）、discovery/pipelineへの統合テスト追加（STEP12/STEP7で追加したテストファイルに追加、計6件）、移行ロジック自体の単体テスト（7件：dry-runで何も変更されないこと、クレンジング、重複統合、公開済み商品が生き残ることの確認、手動データの補完が上書きにならないことの確認、進捗コールバックの確認）。

### 3.5.11 商品名クレンジングの最終強化：空カッコ・表記揺れ重複・スペック文句（STEP19、2026-09-22）

**背景**：STEP18対応後もまだ残っていた残骸・スペック文句の実例：
- 「最大10%OFFクーポン発行中 フォーティーン FR-3 ウェッジ パールサテン N.S.PRO TS-114w Ver2 右利き用 2026年モデル フォーティン FR3 ウェッジ」（クーポン文句・シャフト型番・仕上げ名・利き手属性・年式モデル文句・ブランド名の長音有無表記揺れ）
- 「最大10%OFFクーポン発行中 タイトリスト 2025 プロ V1 ［ ］ PRO V1 ボール」（クーポン文句・中身が空になった全角角カッコの残骸・型番の英字/カタカナ表記重複）

**実装内容（`app/title_cleaner.py`の除去パターン追加）**：
- 中身が空（または空白のみ）のカッコの除去：「［ ］」「[ ]」「（ ）」「()」の4種類全てに対応する`_EMPTY_BRACKET_PATTERN`を新設。既存の`_BRACKET_TAG_PATTERN`（中身のあるカッコタグの除去、全角角カッコ［］は対象外）とは別に、コンテンツ除去処理・ブランド名重複除去処理が終わった後の最終段階で実行し、処理の副産物として空になったカッコも含めて一括除去する。
- 「◯◯年モデル」という年式マーケティング文句の除去（`_YEAR_MODEL_PATTERN`）。ただし「年モデル」のサフィックスを伴わない裸の西暦（例：タイトリストPro V1の実例にある「2025」）はここでは除去しない — ボールのように年式そのものが型番を区別する意味のある情報になりうるケースがあるため、そちらは正規表現層では触らずAI連携層の判断に委ねる設計（後述）。
- クーポン文句の除去：「最大◯%OFF」「クーポン発行中」「クーポン」。
- 仕上げ名・具体シャフト型番の除去：「パールサテン」「ダイヤモンドブラックサテン」を定型文句リストに追加、「N.S.PRO TS-114w Ver2」「NSプロ」「DS-91w」等の具体的なシャフトブランド名＋型番パターンを新設の`_SHAFT_SPEC_PATTERN`で除去（クラブ自身の型番「FR-3」等を誤って除去しないよう、汎用的な英数字コードパターンではなく既知のシャフトブランド接頭辞に限定した設計）。
- 属性文句の除去：「右利き用」「左利き用」「レフティ」「メンズ」「レディース」を定型文句リストに追加。
- ブランド名の表記揺れ重複除去の強化：`app/brands.py`の`BRAND_NAME_SYNONYMS`に、長音記号の有無等による同一ブランドの別表記（「フォーティーン」⇔「フォーティン」）を追加。既存の`_dedupe_brand_name_repeats`ロジックがそのまま対応。

**AIプロンプトの厳格化（`_ai_tighten`のシステムプロンプト）**：「【出力ルール】商品タイトルは『ブランド名＋主要モデル名』のみとし、シャフト名、仕上げ名、右利き/左利き、余計な括弧記号［ ］、および表記揺れの重複はすべて削ぎ落としなさい」という指示を明記。また、実際にテキスト中に存在する年式・年数（裸の「2025」等）を削除するのではなく「モデル名 (年)」という括弧書きに整形してよいという例外を追加（新事実の創作ではなく、既存の年数の表記整形として厳密に限定）。

**既知の制約（正規表現層のみ）**：ブランド名の表記揺れ（`BRAND_NAME_SYNONYMS`に登録済みのもの）は除去できるが、型番自体の異表記重複（「FR-3」⇔「FR3」、「プロ V1」⇔「PRO V1」）はSTEP18同様、辞書化されていない任意の型番の綴り違いを正規表現では認識できないため、正規表現層だけでは統合できない。引き続きClaude API連携層（ANTHROPIC_API_KEY設定時のみ）に委ねる設計とした。本番環境では上記2つの実例は最終的に「フォーティーン FR-3 ウェッジ」「タイトリスト Pro V1 (2025)」まで整形される。

**検証結果**：

### 3.5.12 買い時判定ロジックの緩和とMSRPフォールバック判定（STEP21、2026-09-23）

**背景**：新規発見商品（STEP12以降の自動拡張）は、登録直後は価格履歴が1件（初回取得分のみ）しか無く、`app/analysis.py`の`MIN_HISTORY_POINTS=2`を満たすまで（＝日次バッチが2回以上回るまで）`buy_score="insufficient_data"`のまま表示され続けていた。これが「判定不能」商品が大量発生する主因。ユーザー体験・コンバージョン向上のため、既に実在する事実であるMSRP（定価、手動調査済みデータ）を活用したフォールバック・ブレンド判定を追加した。

**実装内容（`app/analysis.py`）**：
- `analyze_prices()`に新しい任意引数`msrp: int | None = None`を追加（省略時は完全にSTEP21以前と同じ挙動 — 既存の全呼び出し元・全テストは無変更で動作）。
- **価格履歴が0〜1件の場合**：これまでは常に`insufficient_data`だったが、MSRPが分かっており、かつ現在価格が定価より十分安い（`MSRP_STRONG_BUY_RATIO=0.80`未満で`strong_buy`、`MSRP_BUY_RATIO=0.90`未満で`buy`）場合は、`buy_score`を`buy`/`strong_buy`として返すようにした。定価比で十分安くない場合や、定価が無い場合は引き続き`insufficient_data`のまま（**片方向のみ**：`not_buy`/`neutral`という否定的な判定を1件のデータだけから断定することはしない）。
- **価格履歴が2〜3件の場合**：既存の「30日平均との比較」ロジックは変更しないが、それだけで出た判定（`neutral`/`not_buy`）を、MSRP比較の判定（`buy`/`strong_buy`のときのみ）で「格上げ」できるようにした。3件を超えると（`THIN_HISTORY_MSRP_BLEND_MAX_POINTS=3`）このブレンドは適用されず、実データの平均ベース判定のみが使われる（十分な実データがあるときは実トレンドの方が信頼できるため）。実データに基づく`strong_buy`/`buy`判定を、MSRP比較で格下げすることは無い。
- **開発中に発見・修正したバグ**：初期実装では「MSRP判定の方がランクが高ければ格上げ」というロジックだったため、`not_buy`→`neutral`という「買い時ではない」判定同士の格上げも発生し、`neutral`なのに文言が「買い時候補です」になるという表示矛盾を引き起こしていた。修正して、MSRP判定が`buy`/`strong_buy`のときのみ格上げするよう限定（テスト`test_msrp_blend_never_upgrades_not_buy_into_a_mere_neutral`で再発防止）。
- **正直さの担保**：`AnalysisResult`に新フィールド`data_basis`（`"price_history"`＝実データ根拠／`"msrp_estimate"`＝MSRP暫定判定）と`msrp_discount_percent`を追加（DBスキーマ変更は無し、Python内部のデータクラスのみ）。`rule_based_reason()`は`data_basis=="msrp_estimate"`のとき「価格推移データがまだ少ないための暫定判定ですが、定価より◯%安く...」と、実データ根拠の判定とは明確に異なる文言を生成し、架空の「過去30日平均」比較を主張しない。
- **コスト制御**：`app/ai.py`の`generate_ai_content()`が、`data_basis!="price_history"`のときは（`insufficient_data`のときと同様に）Claude API本番呼び出しをスキップし、決定的なルールベース文言にフォールバックするよう変更。この結果、STEP21の変更単体では**Claude API呼び出し回数は一切増加しない**（絶対ルール1: 無断でのコスト発生操作をしない、を厳守）。テスト`test_msrp_estimate_basis_skips_the_live_api_call_even_when_configured`で、実際にAPIクライアントが構築されないことまで検証済み。
- `app/crud.py`の`add_price()`・`app/pipeline.py`の`sync_product_analysis()`（両方とも`analyze_prices()`の呼び出し元）を、`msrp=product.msrp`を渡すよう更新。

**既存商品の再計算**：新しい管理APIエンドポイントは不要 — 既存の`POST /admin/run-update`（管理画面の「分析・AI説明文の再生成」ボタン）が全商品をループして`pipeline.sync_product_analysis`を呼ぶ設計だったため、このボタンを押すだけで新ロジックが全商品に適用される。ローカル開発DB（10商品、テストデータ）で実際に実行し確認：
- 実行前：`insufficient_data` 7件、`neutral` 1件、`not_buy` 2件。
- 実行後：`insufficient_data` 5件、`strong_buy` 3件（いずれもMSRP設定済み・履歴1件のみだった商品）、`neutral` 1件、`not_buy` 1件。
- 新たに`strong_buy`になった3商品の`buy_reason`は「価格推移データがまだ少ないための暫定判定ですが、定価より25.7%/30.0%/35.0%安く、強い買い時候補です。」等、暫定判定であることを明記した文言になっていることを確認。
- **本番への適用**：社長が管理画面で「分析・AI説明文の再生成」ボタンを押すことで、追加コストなしに全商品へ反映できる（Claude API呼び出しは発生しない設計のため）。

**検証結果**：
- `tests/test_analysis.py`に新規テスト11件（MSRPフォールバック発動・不発動の境界、2〜3件ブレンドの格上げ・非格下げ・3件超での不適用、上記バグの再発防止、`rule_based_reason`の文言確認）、`tests/test_ai.py`に新規テスト1件（コスト制御の確認）を追加。
- バックエンド全テスト：既知の無関係なGA4サンドボックス起因の2件を除き、204件全てパス（既存の買い時判定テストは1件も変更せず、全て無改変のまま成功）。`ruff check`もクリーン。

### 3.5.13 型番ごとの最安値集約とカード一元化（STEP22、2026-09-25）

**背景**：楽天市場の異なるショップから同じ型番の商品が発見され、クレンジング後の名前（ブランド＋クリーン商品名）は同じでも、別々のProduct行として登録され続けていた場合、統合（`app/title_migration.py`の統合フェーズ、STEP15由来）自体は行われていたが、**統合後に生き残る行のcurrent_price/product_url/affiliate_url/image_urlが「最も安いショップの出品」ではなく「最も直近に価格取得された出品」になってしまう**という不整合があった（`crud.recompute_current_price`が価格履歴の中で最新タイムスタンプの行を選ぶ設計のため）。価格比較サイトとして「1型番＝1カードで最安値を表示」という理想形に反していたため、統合ロジックを強化した。

**実装内容（`app/title_migration.py`）**：
- 新規`_pick_cheapest_offer(group)`：統合対象グループ内の各商品（＝各ショップの出品）のうち、`current_price`が最も安いものを選び、その価格・`product_url`・`affiliate_url`・`image_url`を**プレーンな値としてロスト前にキャプチャ**（ORMオブジェクトへの参照を後で使うと、既にDELETEされた行にアクセスしてSQLAlchemyの例外になるため）。
- 統合の存続行（survivor）を決めるロジック（`_pick_survivor`：公開済み優先→価格履歴が多い方→古い方）自体は変更していない。「どの行IDが生き残るか」（サイト/SEOの安定性のため）と「生き残った行がどのショップの価格・URL・画像を表示するか」（常に最安値、STEP22の新ルール）を明確に分離した設計。
- 生き残り行の`current_price`/`previous_price`/`product_url`/`affiliate_url`/`image_url`は、統合前のグループ内で最安値だった出品の値に置き換える（`previous_price`には統合前の生き残り行自身の`current_price`を保存し、通常の価格更新と同じ「旧→新」の意味を保つ）。
- 同様に、独立して追跡している`yahoo_price`/`yahoo_url`（第2価格ソース、STEP69）にも同じ「グループ内最安値を採用」ルールを適用（`_pick_cheapest_yahoo_offer`）。統合後も店舗比較表が正直な最安値を示すようにするため。
- `msrp`・`release_date`・`skill_level`・`performance_type`・`is_current_generation`（手動調査済みの事実）は、STEP15以来の「生き残り行が空の場合のみ負け側から補完し、既存値は上書きしない」ルールのまま変更していない——これらは「どのショップが安いか」とは無関係な、商品自体についての事実のため。
- グループ内に価格が判明している商品が1つも無い場合（全出品が価格未取得）は、従来通り`crud.recompute_current_price`（価格履歴の最新行を採用）にフォールバックする。

**安全性**：価格履歴（`PriceHistory`）・`PriceAlert`・`ErrorLog`の負け側から生き残り行への一括付け替えロジック（STEP15由来、SQLの直接UPDATE文でORMのcascade誤動作を回避）は変更していない——今回の変更は「生き残り行のどのフィールドにどの値を採用するか」のみで、データの移動・結合ロジック自体には手を入れていない。

**dry-run検証（ローカル開発DB、`safe-db-migration`スキルの手順に従い実施）**：
```
[統合対象: 1グループ / 計9件]
  testbrand / テスト用ドライバー: 存続 id=1 slug=verify-reliable <- 統合 id=[8, 9, 2, 3, 4, 5, 6, 7]（最安値: id=4 ¥38,000）
```

### 3.5.17 sitemap.xmlのlastmod無効エラー修正（STEP26、2026-09-25）

**背景**：Google Search Consoleでsitemap.xmlを送信した際、「無効な日付：日付の値が無効です (タグ: lastmod)」が50件発生していたとの報告。

**原因調査**：`app/sitemap.ts`の`lastModified`には、商品では`product.updated_at`（バックエンドAPIのレスポンス値）、ガイド記事では`guide.publishedAt`（静的な文字列）をそのまま渡していた。実際にバックエンドを起動してAPIレスポンスを確認したところ、`updated_at`は`"2026-09-25T00:48:09"`のような**タイムゾーン指定（`Z`や`+09:00`等）を含まない**ISO風文字列だった（`app/models.py`の`updated_at`カラムは`server_default=func.now()`でDB側のUTC時刻を使っているが、シリアライズ時にタイムゾーン情報が付与されない）。W3C Datetime/RFC 3339の仕様上、時刻付きの日付文字列はタイムゾーン指定が必須（日付のみの場合は省略可）であり、この形式は仕様上「無効」と判定される。

さらにNext.jsの実装（`node_modules/next/dist/build/webpack/loaders/metadata/resolve-route-data.js`）を確認したところ、`lastModified`に**実際の`Date`オブジェクト**を渡した場合のみ`.toISOString()`で正しくシリアライズされ、**文字列をそのまま渡した場合は一切の検証・変換なしにXMLへそのまま出力される**設計だった。これが、バックエンドのタイムゾーン無し文字列がそのままGoogleに送信され、無効判定を受けていた直接の原因。

**修正内容（`frontend/app/sitemap.ts`）**：
- 新規ヘルパー関数`toLastModified()`を追加：文字列をチェックし、時刻部分（`T`を含む）があるのにタイムゾーン指定が無い場合は明示的に`Z`（UTC）を付与してから`Date`オブジェクトに変換。日付のみの文字列やタイムゾーン指定済みの文字列はそのまま変換。パースに失敗した場合は`undefined`を返し、無効な`<lastmod>`を二度と出力しないようにした。
- 商品（`product.updated_at`）・ガイド記事（`guide.publishedAt`）の両方の`lastModified`をこのヘルパー経由に変更。Next.js側は`Date`オブジェクトを受け取ると自動的に`.toISOString()`で正しい形式（例: `2026-09-25T00:48:09.000Z`）にシリアライズするため、常に有効な形式が保証される。

**検証結果**：
- ローカルでバックエンド・フロントエンドを実際に起動し、`/sitemap.xml`の実出力を確認。全ての`<lastmod>`値が`Z`（UTC）付きの正しい形式（例: `<lastmod>2026-09-25T00:48:09.000Z</lastmod>`）になっており、タイムゾーン無しの日時文字列が1件も残っていないことを確認済み。
- `npm run build`（TypeScript込み）・`npm run lint`ともにエラー無し（既存の無関係な警告1件を除く）。
- バックエンド側のロジック・APIレスポンス形式自体は変更していない（修正はフロントエンドの受け取り側のみ、ご指示の範囲に厳密に限定）。
