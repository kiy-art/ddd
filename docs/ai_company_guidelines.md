Roomと管理画面にも同じ優先順位を実データのまま表示する（3.5.34参照）。STEP44で、「効果測定で『悪化』と出た変更を自動で元に戻す」仕組みを追加した（社長の「すすめて」によるご承認）。7日後の効果測定で商品説明の自動リライトが「悪化」（検索CTRまたはPVが10%以上低下）と判定され、かつ変更前後の数値が十分な実データ（検索表示20回以上、またはPV10以上）に基づく場合に限り、AIが自動で元に戻す。元に戻す際は、数日前の文面に古い価格が残っている可能性（景品表示法上のリスク）があるため、復元後すぐに最新の価格データで通常の文面を再生成する。この再生成にかかりうるClaude呼び出しは1日3件の上限から差し引くため、1日の呼び出し回数は増えない。サンプルが少ない場合の「悪化」は記録のみ残して自動では戻さず、社長の判断に委ねる。差し戻した商品は7日間は再リライトの対象から外し、差し戻し後の新しい数値で改めて判断する。差し戻しの事実と理由は効果測定の記録・ログ・毎朝のAI会議レポート・War Room・管理画面に明記される（3.5.35参照）。STEP45で、「X手動投稿用テキストとOGPを、SNSでのCTR・インプレッションを最大化するプロ仕様に改修してほしい（フック・直感的なお得感・CTA・絵文字、グレーのカードにならないOGP画像）」という依頼を受けた。ローカルで本番ビルドを起動して実際のOGPタグと画像を確認したところ、**カテゴリページ（`/category/...`）とガイド記事ページ（`/guides/...`）には`og:image`が1つも出力されていなかった**（ページ側の`openGraph`設定がサイト共通の画像設定を上書きして消していた）。2商品を紹介するX投稿は常にカテゴリページへリンクしていたため、これがグレーのカードになる直接の原因だった。両ページ専用のOGP画像を新設し、商品ページのOGP画像は商品写真・定価からの値引き額・事実に基づく見出し（「過去14日間の最安値」「定価のほぼ半額」等）を入れたデザインに刷新、バックエンドが休止中で応答しない場合も5秒でブランド入りの画像に切り替わるようにした。投稿文面は「フック→商品名→価格とお得額→買い時スコア→CTA→URL→ハッシュタグ」の型に刷新し、リンクは常に1本目の商品ページ（写真入りカード）に統一した。煽り表現は、事実データで裏付けられる場合にだけ出す（「最安値」は価格履歴7日以上、「半額以下」は四捨五入前の正確な割引率、「楽天ランキングN位」は3日以内の順位）。実装中に、49.7%引きが四捨五入で50%となり「半額以下」と表示されてしまう景品表示法上の不具合を発見し、修正した（3.5.36参照）。STEP46で、「一部の商品画像・カード画像が表示されない（崩れる・読み込まれない）」問題の修正依頼（remotePatterns確認、NO IMAGE代替表示、http→https化）を受けた。調査の結果、画像は全て`unoptimized`（最適化サーバーを通さず元画像をそのまま表示）で読み込んでいるため`remotePatterns`の設定は表示に影響しておらず原因ではないこと、読み込み失敗時の代替表示の仕組み自体は既にあったことが判明した。実際に表示が崩れうる原因として、空白だけ・`http://`・`//`始まり・相対パス等の不正な画像URLがそのまま使われていたこと、参照元（Referer）付きの直リンクを拒否する画像サーバーがあることへの対策が無かったことを特定し、画像URLの正規化処理（`lib/imageUrl.ts`）とPAR.ロゴ入りの「NO IMAGE」代替表示を全ての商品画像に適用した。`remotePatterns`は依頼通り、実際の画像取得元（楽天・Yahoo!）を登録した（3.5.37参照）。

## 3. 現在のシステム構造（調査結果）

### 3.1 技術スタック

- **バックエンド**: FastAPI + SQLAlchemy（本番: Postgres on Render / ローカル: SQLite）
- **フロントエンド**: Next.js（App Router）+ Tailwind CSS v4
- **AI文章生成**: Anthropic Claude API（`app/ai.py`）— 事実の分析結果をもとに紹介文を生成するだけで、買い時判定そのものはルールベース（後述）
- **デプロイ**: Render（`golf-deals-backend` / `golf-deals-frontend`、`render.yaml`で定義）
- **日次バッチ**: GitHub Actions（`.github/workflows/update-prices.yml`）→ `POST /api/admin/fetch-rakuten` を1日1回叩く
  - **重要な訂正（2026-09-22）**：「Renderの無料Cron」という表現が過去の指示に出てきたことがあるが、**Renderの公式Cron Jobsサービスは無料ではない**（1ジョブあたり月額最低$1〜の従量課金、無料プランの対象外）。実際に無料で動いているのはRenderのCronではなく、**GitHub Actionsのスケジュール実行（`schedule: cron`）から、無料のRender Web Service（`golf-deals-backend`）のHTTPエンドポイントを1日1回叩く**という構成。今後「Renderの無料Cron」という指示が来た場合は、このGitHub Actions方式を指すものとして扱う（Renderの有料Cron Jobsサービスは絶対ルール1により無断では契約しない）。

### 3.2 データ取得・保存パイプライン

1. **価格取得**（`app/rakuten.py`, `app/yahoo.py`）
   - 楽天市場「商品検索API」: メインの価格ソース。キーワード検索結果の中央値に最も近い価格を採用（外れ値の誤マッチを避けるため、最安値ではなく中央値ベースで選ぶ）。
   - Yahoo!ショッピング「商品検索API」（本セッションで追加）: 独立した第2の価格ソース。`yahoo_price`という別カラムに保存され、`current_price`や`buy_score`など楽天ベースの分析には一切影響しない設計。
   - 両方とも、価格が異常値（参考価格の0.5〜2.0倍の範囲外）またはアクセサリ/パーツらしき商品名の場合は自動反映せず、`ErrorLog`に記録してスキップする。
2. **保存**（`app/crud.py`）: `PriceHistory`テーブルに追記。`current_price`/`average_price`（30日平均）/`lowest_price`（全期間最安）/`price_change_percent`を再計算。
3. **買い時判定**（`app/analysis.py`）: ルールベースのスコア（`buy_score`: strong_buy/buy/neutral/not_buy/insufficient_data）と0-99の`buy_signal_score`を算出。**AIは一切関与しない**（同じ入力からは常に同じ結果）。
4. **価格予測**（`app/forecast.py`）: 商品自身の価格履歴に対する線形トレンド予測。信頼度（high/medium/low）はデータ量・期間で決まる。発売から60日未満の商品は信頼度を強制的にlowにする（発売直後価格は定価付近に固定されがちなため）。
5. **AI文章生成**（`app/ai.py`）: 上記の事実が変化した場合のみClaude APIを呼び出す（`content_hash`による差分検知でコスト制御）。`insufficient_data`の商品やAPIキー未設定時は生成しない。
6. **新商品の自動発見**（`app/discovery.py`）: 楽天のカテゴリ検索から新商品候補を発見し、`pending_review=True`で作成。**管理者が承認するまで一般公開されない**（誤マッチ・中古品混入を防ぐため）。

### 3.2.1 日次ジョブの堅牢化（2026-09-22）

`POST /admin/fetch-rakuten`は1リクエストの中で「楽天価格取得→Yahoo価格取得→新商品発見→人気ランキング同期→全商品の買い時再分析→値下がり通知メール送信」を順に実行する、実質的に日次バッチ処理そのもの。以下の対策で、**どこか1ステップが予期せぬ例外を出しても、それ以降のステップ（特に最後に実行される値下がり通知メール）が止まらないようにした**：

- 各ステップを個別の`try/except`で囲み、失敗した場合は`db.rollback()`してから次のステップへ進む（`db.rollback()`が無いと、Postgres環境では失敗後のセッションで以降のクエリが全て失敗する — 実際に踏みかねなかった不具合）。
- 商品ごとの再分析ループも1商品の失敗で全体が止まらないよう個別に保護（従来ルーターにはこの保護が無かった。`scripts/update_prices.py`側には元々あったので、両者を揃えた）。
- ジョブの最後に必ず`ErrorLog`（`source="daily_job"`, `level="info"`）へ実行結果サマリーを1件書き込む。`/admin/logs`は新しい順に並ぶため、日次ジョブが最後まで到達したかどうかを管理画面で一目で確認できる（GitHub Actionsのログを見に行かなくてよい）。
- `.github/workflows/update-prices.yml`側も強化：
  - Renderの無料Webサービスは15分アイドルでスリープするため、本処理の前に軽いヘルスチェックで先に起こす（`continue-on-error: true`、失敗しても本処理に影響しない）。
  - `curl --max-time`を180秒→900秒に延長（商品数が増えるほど各API呼び出し間隔（約1.1秒/件）の積み重ねで所要時間が伸びるため）。
  - `--retry 1 --retry-delay 60 --retry-all-errors`でネットワーク瞬断やRenderの再起動に対して1回だけ自動リトライ（パイプラインは冪等に近い設計＝2回走っても致命的な不整合は起きない）。
  - ジョブ全体に`timeout-minutes: 35`（リトライ込みの最悪ケースを想定）。
  - 実行結果をGitHub ActionsのStep Summaryにも出力（失敗時も出す）。スケジュール実行が失敗した場合はGitHubがリポジトリオーナーに自動でメール通知する（追加設定不要）。
- 検証：`backend/tests/test_api.py::test_fetch_rakuten_survives_a_step_blowing_up`で、新商品発見ステップが例外を投げても値下がり通知ステップまで実行されることを確認済み。

### 3.3 「ANALYZING」問題と現状のフォールバック処理

- フロントエンドの`AiBuySignal.tsx`は、`buy_score === "insufficient_data"` または `history_span_days < 7日` の場合、スコアゲージを「フォールバック表示」に切り替える（**解決済み・2026-09-22**）。

  - `history_span_days === 0`のときに「0日分」と表示していた箇所（`ProductCard.tsx`/商品詳細ページ/`compare/page.tsx`）はすべて「登録されたばかりの商品です」等の文言に変更済み。

### 3.5.3 sitemap.xmlの堅牢化（STEP10、2026-09-22）

**きっかけ**：Google Search Consoleにsitemap.xmlを送信したところ「27件のエラー」「検出されたページ数: 0」というエラーが発生。

**根本原因（特定結果）**：`app/sitemap.ts`が商品・ブランド一覧をバックエンドAPIから取得する際、取得に失敗すると例外を`try/catch`で握りつぶし、空配列を返していた。Renderの無料プランはアイドル状態からのコールドスタート（数十秒かかることがある）が発生するため、Googlebotがクロールしたタイミングでバックエンドが起動中/応答遅延だった場合、商品・ブランドURLが一切含まれない（静的ページのみの）不完全なsitemap.xmlが生成されていた可能性が高い。さらに`revalidate`指定が無く、毎回のリクエストでバックエンドへの生存確認から始まる作りだったため、遅延・タイムアウトのリスクが常に存在していた。

**対応内容**：
- `export const revalidate = 3600`（1時間ごとのISR）を追加。クロールのたびにバックエンドへ問い合わせる代わりに、生成済みのsitemapをキャッシュから高速に返す（ローカル検証：初回308ms→キャッシュヒット時21ms）。
- 商品・ブランド取得失敗を握りつぶす`try/catch`を廃止。取得に失敗すると例外がそのまま伝播し、Next.jsのISRは直前に生成できた正常なsitemapを配信し続け、次回リクエストで再試行する（`node_modules/next/dist/docs/01-app/02-guides/incremental-static-regeneration.md`に明記された挙動）。空の不完全なsitemapを配信し続ける事態を防ぐ。
- バックエンド呼び出しに8秒のタイムアウトを追加（コールドスタート中の応答待ちでルート全体が長時間ハングするのを防ぐ）。
- 空/未設定のslug・ブランド名を除外し、URL単位の重複除去を追加。
- `next.config.ts`に`trailingSlash: false`を明示（サイト全体の既存の挙動と一致させ、今後の曖昧さを排除）。

**検証結果**：
- `npm run build`・`eslint`：エラーなし。
- 生成したsitemap.xmlをXMLパーサーで構造検証（`urlset`名前空間、絶対URL、priority範囲0-1、changefreq列挙値、lastmod書式、重複`<loc>`の有無）：問題なし。
- バックエンドを意図的に停止した状態でsitemap.xmlにアクセスし、0.19秒でHTTP 500（空の不完全なsitemapを200で返す旧挙動ではなく、明確な失敗として扱われることを確認）。バックエンド復旧後は正常なsitemap.xmlが返ることを確認。

### 3.5.4 X（Twitter）自動投稿機能（STEP11、2026-09-22）

**背景**：フェーズ2（集客と売上発生）の第一弾。Amazonアソシエイト本審査（3.5参照、直近180日で3件以上の適格販売が必要）を最速で通すため、SEOが育つまでの即効性のある集客手段としてXへの自動投稿を追加した。

**実装内容**：
- 新規モジュール`app/x_post.py`。日次バッチ（`/admin/fetch-rakuten`・`scripts/update_prices.py`）の**最後の工程**として実行される（価格更新・AI再生成・価格アラートより後）。手動実行用に`/admin/post-to-x`エンドポイントと、管理画面に「今すぐ投稿」ボタンも追加（他の任意連携＝Yahoo取得・値下がり通知と同じパターン）。
- **商品選定ロジック**（`select_deals_of_the_day`）：3.3で確立した「実データ優先・フォールバックは補完」の二段構成を再利用。
  1. 第一候補：`buy_score`が`strong_buy`/`buy`かつ`buy_signal_score`があり、価格履歴が`RELIABLE_TREND_MIN_HISTORY_DAYS`（7日）以上ある商品（＝フロントの`THIN_DATA_DAYS`と同じ「信頼できる実シグナル」基準）。
  2. 第二候補（1で規定数に満たない場合のみ）：定価（MSRP）からの割引率が大きい順（値上がり・定価不明の商品は対象外）。
  3. どちらの基準も満たす商品が無い日は**何も投稿しない**（存在しない「お得情報」を捏造しない）。
  - `crud.list_products(published_only=True)`は使わない。このゲートは`buy_score == "insufficient_data"`の商品を一覧から除外する仕様（3.3のANALYZING調査で判明した「一覧には出ないが商品ページ自体は生きている」という既知の区別）だが、フォールバック候補としてはまさにこの層を見る必要があるため。
- **投稿文生成**：Claude API（`app/ai.py`と同じ呼び出しパターン）に、事前計算済みの事実（商品名・現在価格・定価・割引率・買い時判定）のみを渡し、それ以外の数値を創作しないよう厳格なシステムプロンプトで指示。URLはAIには書かせず、コード側で実際のslugから機械的に生成して末尾に付与する（`app/ai.py`で確立した「AIは数字を創作しない」原則の踏襲）。Claude API呼び出しが失敗した場合はルールベースの定型文にフォールバックし、投稿自体は続行する。
- **文字数管理**：X独自の「加重文字数」（日本語等の非ラテン文字は2文字分としてカウント、URLは実際の長さに関わらず23文字固定）を近似計算し、280文字を超える場合は安全に切り詰めて「…」を付与する。
- **認証方式**：OAuth 1.0a（ユーザーコンテキスト、HMAC-SHA1署名）を採用。無料枠のApp-onlyトークンは投稿権限が無いため、X Developer Portalの「Keys and tokens」で発行するAccess Token/Secret（有効期限なし、アプリのPermissionsを"Read and Write"に設定した上で発行）が必要。SDKは使わず、既存コードの`httpx`直接呼び出しのスタイル（`rakuten.py`/`yahoo.py`/`email.py`）に合わせて自前で署名。
- **安全な組み込み（例外分離）**：投稿処理全体を独自の`try/except`で囲み、失敗時は`db.rollback()`の上で`ErrorLog`に記録するのみで、日次バッチ本体（価格更新・値下がり通知等）には一切影響しない設計（3.2.1で確立したパターンを踏襲）。この分離が実際に機能することをテスト（`test_fetch_rakuten_survives_x_post_blowing_up`）で確認済み。
- **未設定時の挙動**：`X_API_KEY`/`X_API_SECRET`/`X_ACCESS_TOKEN`/`X_ACCESS_TOKEN_SECRET`の4つが揃っていない場合は、エラーにはせず単純に投稿をスキップする（`YAHOO_CLIENT_ID`/`RESEND_API_KEY`と同じ「未設定でも安全に動く」設計）。

**必要な環境変数（Renderに登録が必要）**：
| 変数名 | 内容 |
|---|---|
| `X_API_KEY` | X Developer PortalのApp「Consumer Keys」→ API Key |
| `X_API_SECRET` | 同上 → API Key Secret |
| `X_ACCESS_TOKEN` | 同Appの「Keys and tokens」→ Access Token（Permissionsを"Read and Write"にしてから生成） |
| `X_ACCESS_TOKEN_SECRET` | 同上 → Access Token Secret |

※`ANTHROPIC_API_KEY`（設定済み）は投稿文のAI生成にも流用される。未設定でもルールベース文面で投稿自体は継続する。

**⚠️ 未解決事項：X APIの無料枠の条件について**：本タスク指示にあった「無料枠の月1,500件投稿」について確認のためWebSearchを行ったが、情報源によって内容が一致しなかった（一部の非公式情報源は2026年2月以降Freeプラン自体が廃止され新規開発者は従量課金制のみになったと主張しており、公式ドメイン`developer.x.com`由来と見られる検索結果内でも「1,500 Posts/month」という記述と、v2 API限定で「500 Posts and 100 Reads per month」という記述が混在していた）。**コードの実装自体は無料（認証情報を設定するまで一切課金は発生しない）だが、実際にXデベロッパーアカウントを登録する前に、必ず`developer.x.com`で現在の正式な料金条件をご自身で確認してください。** 万一「投稿にも有料プランが必要」という条件だった場合は、絶対ルール1（コストが発生する操作は事前許可が必要）により、登録・API利用を進める前にご相談ください。

### 3.5.5 商品カタログの安全な自動拡張（STEP12、2026-09-22）

**背景**：Amazonアソシエイト本審査（3.5参照）に必要な「直近180日で3件以上の適格販売」を最速で達成するため、購入ハードルが低く回転率の高い消耗品（ゴルフボール等）を中心に商品数を拡大する方針。

**実装内容（`app/discovery.py`）**：
- **検索キーワードの拡張**：`CATEGORY_SEARCH_KEYWORDS`をカテゴリ→単一キーワードからカテゴリ→キーワード一覧に変更。driver/iron/wedge/putterは既存通りカテゴリ自体は既に検索対象済み（新規追加ではなく既存動作の確認）。ゴルフボールのみ、汎用キーワード（「ゴルフボール 1ダース 新品」）に加え、中級者以上が指名買いする定番モデル名（Titleist Pro V1、スリクソン Z-STAR、ブリヂストン TOUR B）を個別キーワードとして追加。汎用検索は無名の安価な詰め合わせに偏りやすいため、モデル名を直接検索することで確実に拾う。
- **1回の検索あたりの取得件数**：Rakuten Ichiba商品検索APIの1リクエストあたり上限（30件）まで引き上げ（旧: 10件）。
- **カテゴリごとの新規追加上限**（`MAX_NEW_PER_CATEGORY`）：3件→20件に引き上げ（カテゴリ内の全キーワード合算）。複数キーワードを持つカテゴリ（ボール）は上限に達した時点で残りのキーワード検索自体をスキップし、Rakuten APIへの無駄なリクエストを避ける。
- **安全な自動公開フィルター（新機能）**：これまで自動検出商品は例外なく`pending_review=True`（承認待ち）だったが、以下の**両方**を満たす商品のみ`pending_review=False`（即時公開）にする（`_is_safe_to_auto_publish`）：
  1. NGワード（`AUTO_PUBLISH_NG_KEYWORDS`：「中古」「ヘッドカバー」「シャフトのみ」「スリーブ」「用」）を商品名に含まない。
  2. 価格が閾値以上：ボールは3,000円以上、クラブ類（driver/iron/wedge/putter）は10,000円以上。
  - この判定は「候補として採用するかどうか」（既存の`_looks_like_accessory`・`MIN_DISCOVERY_PRICE`・ブランド一致判定、変更なし）とは独立した**追加の**判定であり、両方の基準から外れる、または際どい商品は従来通り承認待ちのまま安全側に倒す。
- **表示テキストの修正**：管理画面「商品の自動検出」カードおよび各種完了メッセージが「自動検出された商品は承認するまで公開されない」という、STEP12で実態と食い違うことになった文言だったため、安全な商品は自動公開される旨に修正（実際の挙動と表示文言が食い違う既知の不具合パターン ── 3.5.1のホームページbestBuyバグと同種 ── を未然に防止）。

**安全設計の考え方**：「採用するかどうか」のフィルター（アクセサリ除外・最低価格・ブランド一致）は一切変更していない。今回変更したのは、既に候補として採用された商品のうち「即時公開して良いか、人の確認を待つか」の判定のみ。判定に迷う・際どい商品は必ず安全側（承認待ち）に倒れる設計とした。

**運用上の留意点**：Rakutenの検索結果は日によって大きくは変わらないため、同日中に「今すぐ検出」を複数回クリックしても新規追加件数は伸びにくい（重複除去が効くため）。「数百件規模」への到達は、今回追加したキーワードの幅と引き上げた上限により1回の実行での新規追加数を底上げしつつ、日次自動バッチによる継続的な蓄積（Rakutenの人気ランキング変動・新規出品の反映）を通じて段階的に進む見込み。即座に数百件へ到達することを保証するものではない。

### 3.5.6 管理画面のリアルタイム・ライブダッシュボード（STEP13、2026-09-22）

**背景**：日次バッチ処理（楽天価格取得→新商品探索→人気ランキング同期→買い時判定・AI説明文生成→値下がり通知→SNS投稿）が今どの工程にいるか、管理画面上で視覚的にリアルタイム把握できるようにする要望。

**実装内容**：
- **配信方式**：Server-Sent Events（SSE）を採用。WebSocketsではなくSSEを選んだ理由は、配信方向が「サーバー→ブラウザ」の一方向で十分なため（ブラウザからサーバーへの追加メッセージは不要）、FastAPIの標準機能`StreamingResponse`だけで実装でき、Pusher等の有料/サードパーティ製リアルタイム通信サービスが一切不要なため。
- **新規モジュール`app/progress.py`**：プロセス内（インメモリ）のpub/sub。Renderの無料プランのバックエンドはuvicornワーカー1個のみで動作している（`render.yaml`の`startCommand`に`--workers`指定なし、3.1参照）ため、Redis等の外部ストアなしで「プロセス内の購読者リストにブロードキャストする」だけの単純な実装で足りる。**将来バックエンドを複数ワーカー/複数インスタンスに拡張する場合はこの前提が崩れる**ため、その際はRedis等の外部pub/subへの置き換えが必要になる旨をコード内コメントに明記。
- **配信の粒度**：「ジョブ（例：日次バッチ全体、または個別の「今すぐXX」ボタン1つ）」の中に複数の「ステージ」（市場価格取得中・新商品探索中・人気ランキング同期中・買い時判定AI生成中・値下がり通知送信中・SNS投稿中）があり、各ステージの開始・進捗（件数/全体件数）・完了を逐次配信する。楽天/Yahoo!価格取得・新商品探索・買い時判定の3ステージは実際に処理件数が数百件規模になりうる（STEP12参照）ため、`on_progress`コールバック（オプション引数、既存の呼び出し元には一切影響しない設計）を`pipeline.fetch_rakuten_prices`/`fetch_yahoo_prices`/`discovery.discover_new_products`に追加し、1件ごとに進捗を報告できるようにした。買い時判定ステージは全商品ループが速いため、5件ごとに間引いて配信（無駄なイベント過多を防止）。
- **既存の日次ジョブ（`/admin/fetch-rakuten`）・個別手動実行エンドポイント（`/admin/run-update`、`/admin/fetch-yahoo`、`/admin/send-price-alerts`、`/admin/post-to-x`、`/admin/sync-popularity`、`/admin/discover-products`）すべてに組み込み**：どのボタンを押しても同じライブダッシュボードに反映される。
- **新規エンドポイント`GET /admin/live`**：SSEストリームを配信。接続直後に「現在（または直近に完了した）ジョブの状態」を1件即座に送るため、実行中に開いても空白にならない。15秒ごとにキープアライブコメント行を送信（Renderのプロキシ等がアイドル接続を切断するのを防止）。
- **重要な実装上の注意（認証）**：ブラウザ標準の`EventSource`はカスタムヘッダーを送れないため、このAPIが要求する`Authorization: Bearer <token>`ヘッダー（Cookie未使用、`app/auth.py`）を送信できない。そのため`EventSource`ではなく、`fetch()` + `ReadableStream`を手動でパースする方式をフロントエンドで採用（新規`lib/useLiveJobUpdates.ts`）。ネットワーク切断時は3秒後に自動再接続。
- **フロントエンド**：管理画面トップ（`/admin`）に「実況ダッシュボード」カードとして常設（別ページへの遷移は不要 — どの「今すぐXX」ボタンを押しても画面遷移せずそのまま進行状況が見られる）。新規コンポーネント`components/LiveJobDashboard.tsx`：ステージごとに進行中（パルスアニメーション）/完了（チェック相当の静的表示）を視覚的に区別し、件数が分かるステージにはプログレスバーを表示。

**検証結果**：
- バックエンド：新規`tests/test_progress.py`（pub/sub機構の単体テスト、スナップショットの不変性 — 実際に開発中に検出した「キュー投入後のミューテーションでイベント内容が後から書き換わる」バグの回帰テストを含む — 7件）、`tests/test_api.py`に日次ジョブが実際に正しいステージ順で完了状態を記録することを検証するテストを追加。全156件中、既知の無関係なGA4サンドボックス起因の2件を除き全てパス。
- フロントエンド：`npm run build`・ESLintともにエラーなし。
- **実機検証**：ローカルでバックエンド（uvicorn）・フロントエンド（next dev）を起動し、Playwrightで実際にブラウザから管理画面にログイン→「今すぐ実行」を押下→ライブダッシュボードが「実行中」から「完了」へ、ステージ名・件数・プログレスバーとともに正しく更新されることをスクリーンショットで確認済み。
- **既知の制約**：SSEの無限ストリーム自体をテストクライアント（`fastapi.testclient.TestClient`、内部的にhttpxのASGIトランスポートを使用）経由で自動テストしようとすると、このテスト環境ではストリームの読み取りがハングすることを確認した（本物のネットワーク接続ではなく、テスト用のインプロセスASGIトランスポートの既知の制約と考えられる）。そのため自動テストはSSE配信の中身（`app/progress.py`の単体テスト）と、認証拒否時に即座に401が返ること止まりとし、ストリーミング自体の動作確認は上記の実機（Playwright）検証で代替した。

### 3.5.7 店舗比較表のバグ修正とコンバージョン最適化（STEP14、2026-09-22）

**きっかけ**：「Yahoo!ショッピングの行が比較表から抜け落ちる」という不具合報告と、「Amazonの文言が消極的」「楽天を推しすぎている（回し者に見える）」というUI公平性の課題。

**原因調査結果（Yahoo!非表示バグ）**：`components/StoreComparisonTable.tsx`・バックエンドのスキーマ（`ProductOut`/`ProductDetailOut`に`yahoo_price`/`yahoo_url`含む）・APIルーター（`GET /api/products/{slug}`）を一通り確認したが、**いずれもコード自体にバグは無かった**。ローカルで実際にDBへYahoo!価格データを投入し、フロントエンドが正しくレンダリングすることを実機（Playwright）で確認済み。つまり「バグ」の実体は、**元々の設計が「そのモールで実際に価格が見つかった場合のみ行を表示し、見つからない場合は行ごと消す」という仕様だった**こと。楽天は`current_price`（商品自体の主価格）が必ずあるため常に表示される一方、Yahoo!は「マッチが見つからない日」や「YAHOO_CLIENT_ID未設定の環境」では行自体が消え、あたかも「取得できているはずなのに表示されない」ように見えていた。これはコードの欠陥というより、**「データが無いなら黙って隠す」という設計判断そのものが、期待される見え方（3社は常に並んで見えるべき）とズレていた**という設計上の問題であり、同時に「楽天ばかり目立つ」というUI公平性の課題とも直接つながっていた（第2・第3のモールが条件次第で消えるため、結果的に楽天だけが常に主役に見える）。

**対応内容**：
- **Yahoo!ショッピングの行を常時表示に変更**：実際の価格が取得できていればその価格とリンクを表示し、取得できていない場合は（Amazonの既存行と同じ考え方で）Yahoo!ショッピングの検索結果ページへの通常リンク（アフィリエイトタグなし・無報酬、`lib/yahoo.ts`新規作成）にフォールバックする。行が条件次第で消えることが無くなった。
- **Amazonのマイクロコピー改善**：ボタン文言を「Amazonで探す →」→「Amazonで最安値をチェック →」に、価格欄横の説明文を「商品名の検索結果ページが開きます」→「Amazon内の価格をチェック（最安値の可能性あり）」に変更。事実として断定できない「最安値かもしれない」という可能性ベースの表現に留め、誇大表示にはしていない。
- **ボタンデザインの差別化（原則ベース）**：「確定価格が分かっている行」（楽天・Yahoo!の実データ）は従来通りの控えめなアウトライン、「価格は不明だが確認する価値がある行」（Amazon・Yahoo!未マッチ時のフォールバック）はブランドカラーの塗りつぶしボタンに変更しクリックを誘発。この差別化は**「特定のモールだから」ではなく「価格が分かっているかどうか」という状態に基づく原則的なルール**にしており、日によってどのモールがどちらの見た目になるかは変わる（例：Yahoo!に実データがあればYahoo!も控えめな表示になる）。メーカー公式サイトの行は「最安値の可能性」という表現が実態と合わない（定価販売が基本）ため、この強調対象からは除外。
- **テーブルの並び順を「価格が安い順」に変更**：従来はコード内の記述順（楽天→Yahoo→公式→Amazon）で常に楽天が先頭だった。実際の価格が判明している行を安い順に並べ、価格不明の行は末尾に回すことで、**その日実際に最安値のモールが自然に先頭へ来る**ようにした。「楽天が常に一番目立つ」という構造的な偏りを解消。
- 分析イベント（`cta_click`の`cta_type`）に、Yahoo!の検索フォールバック用の新しい区分（`marketplace_search`）を追加（従来は誤って`official`扱いになっていた）。

**検証結果**：
- `npm run build`（TypeScript込み）：エラーなし。
- 実機検証（Playwright）：①Yahoo!に実データがある場合に正しく表示され、価格が最安なら「最安」バッジと共に先頭に来ることを確認。②Yahoo!に実データが無い場合、行が消えずに検索リンクへのフォールバックとボタンが表示されることを確認。③デスクトップ幅・モバイル幅の両方でレイアウト崩れが無いことを確認（モバイル時の横スクロール自体は本改修以前からの既存仕様で、今回変更していない）。

### 3.5.12 買い時判定ロジックの緩和とMSRPフォールバック判定（STEP21、2026-09-23）

**背景**：新規発見商品（STEP12以降の自動拡張）は、登録直後は価格履歴が1件（初回取得分のみ）しか無く、`app/analysis.py`の`MIN_HISTORY_POINTS=2`を満たすまで（＝日次バッチが2回以上回るまで）`buy_score="insufficient_data"`のまま表示され続けていた。これが「判定不能」商品が大量発生する主因。ユーザー体験・コンバージョン向上のため、既に実在する事実であるMSRP（定価、手動調査済みデータ）を活用したフォールバック・ブレンド判定を追加した。

**実装内容（`app/analysis.py`）**：
- `analyze_prices()`に新しい任意引数`msrp: int | None = None`を追加（省略時は完全にSTEP21以前と同じ挙動 — 既存の全呼び出し元・全テストは無変更で動作）。
- **価格履歴が0〜1件の場合**：これまでは常に`insufficient_data`だったが、MSRPが分かっており、かつ現在価格が定価より十分安い（`MSRP_STRONG_BUY_RATIO=0.80`未満で`strong_buy`、`MSRP_BUY_RATIO=0.90`未満で`buy`）場合は、`buy_score`を`buy`/`strong_buy`として返すようにした。定価比で十分安くない場合や、定価が無い場合は引き続き`insufficient_data`のまま（**片方向のみ**：`not_buy`/`neutral`という否定的な判定を1件のデータだけから断定することはしない）。
- **価格履歴が2〜3件の場合**：既存の「30日平均との比較」ロジックは変更しないが、それだけで出た判定（`neutral`/`not_buy`）を、MSRP比較の判定（`buy`/`strong_buy`のときのみ）で「格上げ」できるようにした。3件を超えると（`THIN_HISTORY_MSRP_BLEND_MAX_POINTS=3`）このブレンドは適用されず、実データの平均ベース判定のみが使われる（十分な実データがあるときは実トレンドの方が信頼できるため）。実データに基づく`strong_buy`/`buy`判定を、MSRP比較で格下げすることは無い。
- **開発中に発見・修正したバグ**：初期実装では「MSRP判定の方がランクが高ければ格上げ」というロジックだったため、`not_buy`→`neutral`という「買い時ではない」判定同士の格上げも発生し、`neutral`なのに文言が「買い時候補です」になるという表示矛盾を引き起こしていた。修正して、MSRP判定が`buy`/`strong_buy`のときのみ格上げするよう限定（テスト`test_msrp_blend_never_upgrades_not_buy_into_a_mere_neutral`で再発防止）。
- **正直さの担保**：`AnalysisResult`に新フィールド`data_basis`（`"price_history"`＝実データ根拠／`"msrp_estimate"`＝MSRP暫定判定）と`msrp_discount_percent`を追加（DBスキーマ変更は無し、Python内部のデータクラスのみ）。`rule_based_reason()`は`data_basis=="msrp_estimate"`のとき「価格推移データがまだ少ないための暫定判定ですが、定価より◯%安く...」と、実データ根拠の判定とは明確に異なる文言を生成し、架空の「過去30日平均」比較を主張しない。
- **コスト制御**：`app/ai.py`の`generate_ai_content()`が、`data_basis!="price_history"`のときは（`insufficient_data`のときと同様に）Claude API本番呼び出しをスキップし、決定的なルールベース文言にフォールバックするよう変更。この結果、STEP21の変更単体では**Claude API呼び出し回数は一切増加しない**（絶対ルール1: 無断でのコスト発生操作をしない、を厳守）。テスト`test_msrp_estimate_basis_skips_the_live_api_call_even_when_configured`で、実際にAPIクライアントが構築されないことまで検証済み。
- `app/crud.py`の`add_price()`・`app/pipeline.py`の`sync_product_analysis()`（両方とも`analyze_prices()`の呼び出し元）を、`msrp=product.msrp`を渡すよう更新。

**既存商品の再計算**：新しい管理APIエンドポイントは不要 — 既存の`POST /admin/run-update`（管理画面の「分析・AI説明文の再生成」ボタン）が全商品をループして`pipeline.sync_product_analysis`を呼ぶ設計だったため、このボタンを押すだけで新ロジックが全商品に適用される。ローカル開発DB（10商品、テストデータ）で実際に実行し確認：
- 実行前：`insufficient_data` 7件、`neutral` 1件、`not_buy` 2件。
- 実行後：`insufficient_data` 5件、`strong_buy` 3件（いずれもMSRP設定済み・履歴1件のみだった商品）、`neutral` 1件、`not_buy` 1件。
- 新たに`strong_buy`になった3商品の`buy_reason`は「価格推移データがまだ少ないための暫定判定ですが、定価より25.7%/30.0%/35.0%安く、強い買い時候補です。」等、暫定判定であることを明記した文言になっていることを確認。
- **本番への適用**：社長が管理画面で「分析・AI説明文の再生成」ボタンを押すことで、追加コストなしに全商品へ反映できる（Claude API呼び出しは発生しない設計のため）。

**検証結果**：
- `tests/test_analysis.py`に新規テスト11件（MSRPフォールバック発動・不発動の境界、2〜3件ブレンドの格上げ・非格下げ・3件超での不適用、上記バグの再発防止、`rule_based_reason`の文言確認）、`tests/test_ai.py`に新規テスト1件（コスト制御の確認）を追加。
- バックエンド全テスト：既知の無関係なGA4サンドボックス起因の2件を除き、204件全てパス（既存の買い時判定テストは1件も変更せず、全て無改変のまま成功）。`ruff check`もクリーン。

### 3.5.13 型番ごとの最安値集約とカード一元化（STEP22、2026-09-25）

**背景**：楽天市場の異なるショップから同じ型番の商品が発見され、クレンジング後の名前（ブランド＋クリーン商品名）は同じでも、別々のProduct行として登録され続けていた場合、統合（`app/title_migration.py`の統合フェーズ、STEP15由来）自体は行われていたが、**統合後に生き残る行のcurrent_price/product_url/affiliate_url/image_urlが「最も安いショップの出品」ではなく「最も直近に価格取得された出品」になってしまう**という不整合があった（`crud.recompute_current_price`が価格履歴の中で最新タイムスタンプの行を選ぶ設計のため）。価格比較サイトとして「1型番＝1カードで最安値を表示」という理想形に反していたため、統合ロジックを強化した。

**実装内容（`app/title_migration.py`）**：
- 新規`_pick_cheapest_offer(group)`：統合対象グループ内の各商品（＝各ショップの出品）のうち、`current_price`が最も安いものを選び、その価格・`product_url`・`affiliate_url`・`image_url`を**プレーンな値としてロスト前にキャプチャ**（ORMオブジェクトへの参照を後で使うと、既にDELETEされた行にアクセスしてSQLAlchemyの例外になるため）。
- 統合の存続行（survivor）を決めるロジック（`_pick_survivor`：公開済み優先→価格履歴が多い方→古い方）自体は変更していない。「どの行IDが生き残るか」（サイト/SEOの安定性のため）と「生き残った行がどのショップの価格・URL・画像を表示するか」（常に最安値、STEP22の新ルール）を明確に分離した設計。
- 生き残り行の`current_price`/`previous_price`/`product_url`/`affiliate_url`/`image_url`は、統合前のグループ内で最安値だった出品の値に置き換える（`previous_price`には統合前の生き残り行自身の`current_price`を保存し、通常の価格更新と同じ「旧→新」の意味を保つ）。
- 同様に、独立して追跡している`yahoo_price`/`yahoo_url`（第2価格ソース、STEP69）にも同じ「グループ内最安値を採用」ルールを適用（`_pick_cheapest_yahoo_offer`）。統合後も店舗比較表が正直な最安値を示すようにするため。
- `msrp`・`release_date`・`skill_level`・`performance_type`・`is_current_generation`（手動調査済みの事実）は、STEP15以来の「生き残り行が空の場合のみ負け側から補完し、既存値は上書きしない」ルールのまま変更していない——これらは「どのショップが安いか」とは無関係な、商品自体についての事実のため。
- グループ内に価格が判明している商品が1つも無い場合（全出品が価格未取得）は、従来通り`crud.recompute_current_price`（価格履歴の最新行を採用）にフォールバックする。

**安全性**：価格履歴（`PriceHistory`）・`PriceAlert`・`ErrorLog`の負け側から生き残り行への一括付け替えロジック（STEP15由来、SQLの直接UPDATE文でORMのcascade誤動作を回避）は変更していない——今回の変更は「生き残り行のどのフィールドにどの値を採用するか」のみで、データの移動・結合ロジック自体には手を入れていない。

### 3.5.14 タイトリスト Pro V1の重複カード調査と統合ルール強化（STEP23、2026-09-25）

**背景**：サイト上に「タイトリスト Pro V1」のカードが複数表示されているとの報告を受け、原因調査と修正を実施。

**調査方法について**：本セッションの実行環境からは本番DB（Render上のPostgres）に直接アクセスする手段が無い（Web Shellが無いというSTEP16の制約と同じ）ため、本番の実データを直接抽出することはできなかった。代わりに、`clean-product-title`スキルの手順に従い、実際の楽天市場の出品でよく見られる表記パターン（年式表記・セット/球数表記・カラー表記・スペース有無等）を実例として再現し、既存の`app/title_cleaner.py`のロジックに実際に通して原因を特定する形で調査した。

**特定した原因（3件）**：
1. **年式表記のバグ（最重要）**：STEP19で追加した「◯◯年モデル」除去パターン（`_YEAR_MODEL_PATTERN`）が、年式の数字ごと丸ごと削除する設計だったため、「2023年モデル」も「2025年モデル」も同じく空文字列に削除され、**明確に異なる世代の商品が同じクレンジング後の名前に収束して統合されてしまう**（意図とは逆に、区別すべきものを誤って同一視する）バグがあった。ゴルフクラブでは「年モデル」表記はほぼ純粋なマーケティング文句だが、ゴルフボール（Pro V1等）は実際に約2年周期で仕様が変わる世代性のある商品であり、年式は商品を区別する実情報だった。
2. **セット/球数表記の残骸**：「(12球)」のように「入り」を伴わない半角カッコの球数表記が、既存の`_QUANTITY_PATTERN`（「◯球入り」のみに一致）でも半角カッコの一括除去（意図的に対象外、実スペック情報を誤除去しないため）でも捕捉されず、ノイズとして残っていた。
3. **カラー表記の残骸**：「パールホワイト」のような複合カラー名が、既存の色名リストでは「ホワイト」部分だけにマッチし、「パール」が孤立して残っていた。

**実装内容（`app/title_cleaner.py`）**：
- `_YEAR_MODEL_PATTERN`：「年モデル」という**文言だけ**を除去し、年の数字自体は残すように変更（`\d{4}年モデル`の一括削除 → `(\d{4})年モデル`を`\1`（キャプチャした年）に置換）。「2023年モデル」→「2023」、「2025年モデル」→「2025」となり、同じ年同士は統合対象に、異なる年は別カードのまま維持される。
- **芋づる式に発覚した第二のバグ**：上記の修正を入れたところ、STEP19の`_SHAFT_SPEC_PATTERN`（シャフト型番除去）が貪欲マッチ（`(?:\s*[A-Za-z0-9\-]+)*`、0回以上の繰り返し）になっており、"N.S.PRO TS-114w Ver2" の直後に残った裸の年数字（"2026"等）まで英数字の並びとして一緒に飲み込んでしまうことが判明。`*`（0回以上）を`?`（0または1回）に変更し、シャフト型番1つ分だけにマッチを限定して修正。
- `_QUANTITY_PATTERN`：「◯球」の「入り」を任意（`\d+球(?:入り)?`）にし、「(12球)」のような残骸も除去できるように強化。
- `_PROMO_PHRASES`：「パールホワイト」「パールイエロー」を色名リストに先立って追加し、複合カラー名を一括除去（「パール」の孤立残骸を防止）。
- 統合ロジック自体（`app/title_migration.py`の(brand, クレンジング後の名前)によるグループ化、STEP22の最安値採用ルール）は変更不要 — クレンジングが正しくなれば既存の統合ロジックがそのまま正しく機能する設計だったため。

**確認した「壊してはいけないもの」**：「Pro V1」と「Pro V1x」（型番末尾の"x"で区別される別モデル）が誤って統合されないことを確認済み（型番自体の文字列は正規表現層で一切書き換えていないため、元々問題なし）。「ProV1」（スペース無し）と「Pro V1」（スペース有り）の表記揺れは、既存の「既知の制約」の通り正規表現層だけでは統合できず、Claude連携層に委ねる設計を維持。

**`safe-db-migration`スキルによる検証**：ローカル開発DBに、実際の楽天出品パターンを模した検証データ（同一2023年モデルのPro V1を3ショップ分・異なる年式2025年モデルを1件・別モデルPro V1xを1件）を作成し、dry-run実行：
```
[統合対象: 1グループ / 計3件]
  titleist / タイトリスト pro v1 2023: 存続 id=11 <- 統合 id=[12, 13]（最安値: id=12 ¥5,200）
```

### 3.5.17 sitemap.xmlのlastmod無効エラー修正（STEP26、2026-09-25）

**背景**：Google Search Consoleでsitemap.xmlを送信した際、「無効な日付：日付の値が無効です (タグ: lastmod)」が50件発生していたとの報告。

**原因調査**：`app/sitemap.ts`の`lastModified`には、商品では`product.updated_at`（バックエンドAPIのレスポンス値）、ガイド記事では`guide.publishedAt`（静的な文字列）をそのまま渡していた。実際にバックエンドを起動してAPIレスポンスを確認したところ、`updated_at`は`"2026-09-25T00:48:09"`のような**タイムゾーン指定（`Z`や`+09:00`等）を含まない**ISO風文字列だった（`app/models.py`の`updated_at`カラムは`server_default=func.now()`でDB側のUTC時刻を使っているが、シリアライズ時にタイムゾーン情報が付与されない）。W3C Datetime/RFC 3339の仕様上、時刻付きの日付文字列はタイムゾーン指定が必須（日付のみの場合は省略可）であり、この形式は仕様上「無効」と判定される。

さらにNext.jsの実装（`node_modules/next/dist/build/webpack/loaders/metadata/resolve-route-data.js`）を確認したところ、`lastModified`に**実際の`Date`オブジェクト**を渡した場合のみ`.toISOString()`で正しくシリアライズされ、**文字列をそのまま渡した場合は一切の検証・変換なしにXMLへそのまま出力される**設計だった。これが、バックエンドのタイムゾーン無し文字列がそのままGoogleに送信され、無効判定を受けていた直接の原因。

**修正内容（`frontend/app/sitemap.ts`）**：
- 新規ヘルパー関数`toLastModified()`を追加：文字列をチェックし、時刻部分（`T`を含む）があるのにタイムゾーン指定が無い場合は明示的に`Z`（UTC）を付与してから`Date`オブジェクトに変換。日付のみの文字列やタイムゾーン指定済みの文字列はそのまま変換。パースに失敗した場合は`undefined`を返し、無効な`<lastmod>`を二度と出力しないようにした。
- 商品（`product.updated_at`）・ガイド記事（`guide.publishedAt`）の両方の`lastModified`をこのヘルパー経由に変更。Next.js側は`Date`オブジェクトを受け取ると自動的に`.toISOString()`で正しい形式（例: `2026-09-25T00:48:09.000Z`）にシリアライズするため、常に有効な形式が保証される。

**検証結果**：
- ローカルでバックエンド・フロントエンドを実際に起動し、`/sitemap.xml`の実出力を確認。全ての`<lastmod>`値が`Z`（UTC）付きの正しい形式（例: `<lastmod>2026-09-25T00:48:09.000Z</lastmod>`）になっており、タイムゾーン無しの日時文字列が1件も残っていないことを確認済み。
- `npm run build`（TypeScript込み）・`npm run lint`ともにエラー無し（既存の無関係な警告1件を除く）。
- バックエンド側のロジック・APIレスポンス形式自体は変更していない（修正はフロントエンドの受け取り側のみ、ご指示の範囲に厳密に限定）。

### 3.5.22 自動商品発見の検索キーワード拡充：ブランドの偏りを自動で是正（STEP31、2026-09-25）

**背景**：STEP30（手動でのPING G430/G710等の追加）の直後、「私が何も作業しなくても商品数を更新できないか。CSVの取り込みが面倒」というご質問。

**調査結果**：GitHub Actionsの実行履歴（`mcp__github__actions_list`）と本番バックエンドのジョブ応答を確認した結果、以下が判明した。

- **日次の自動更新ジョブ（`.github/workflows/update-prices.yml`、毎日06:00 JST）は既に正常稼働しており**、直近5回（2026-09-21〜09-24）すべて成功していた。
- このジョブが叩く`POST /api/admin/fetch-rakuten`は、価格取得だけでなく**新商品の自動発見（`app/discovery.py`のdiscover_new_products）も既に含んでいる**（管理画面の「商品の自動検出」ボタンと同じ処理）。
- 直近の実行結果（2026-09-24分、実際のジョブログより）：`products_checked: 162`（本番は既に162商品まで自動成長していた）、`products_discovered: 8`（その日だけで新規8件を自動発見）、`candidates_considered: 210`。
- つまり、**STEP30で私が手動でCSVを作って追加した作業は、複数日待てば自動発見パイプラインが同じような商品を勝手に見つけてきていた可能性が高い**、一回限りの前倒し措置だった。

**根本原因**：`app/discovery.py`の`CATEGORY_SEARCH_KEYWORDS`は、ドライバー・アイアン・ウェッジ・パターについては「ゴルフ ドライバー 新品」のような**汎用キーワード1つのみ**で楽天検索していた（ボールだけは「Titleist Pro V1」等、銘柄名を直接検索する設計だった——STEP12参照）。楽天の検索結果は関連度順に上位30件までしか見ないため、汎用キーワードだと結果的にTaylorMade・Callaway等の露出が強いブランドに偏り、PING・ゼクシオ・本間ゴルフ・ブリヂストンのドライバーや、TaylorMadeのアイアンが検索結果の上位に出てこず、何日待っても自動発見されにくい状態になっていたと考えられる。これがSTEP30で指摘された偏りの根本原因。

**実装内容**：`backend/app/discovery.py`の`CATEGORY_SEARCH_KEYWORDS`に、ボール用キーワードと同じ設計思想（銘柄名で直接検索）をドライバー・アイアンにも適用した。

- driver: 既存の汎用キーワードに加え、`"PING ドライバー 新品"` `"ゼクシオ ドライバー 新品"` `"本間ゴルフ ドライバー 新品"` `"ブリヂストン ドライバー 新品"` を追加。
- iron: 既存の汎用キーワードに加え、`"PING アイアン セット 新品"` `"テーラーメイド アイアン セット 新品"` を追加。
- 具体的なモデル名（G430等）ではなく**ブランド名**で検索する設計にした。モデル名だと数年後にモデルチェンジした際に検索が陳腐化するが、ブランド名なら常にそのブランドの「今売っている」現行ラインナップを拾い続けられるため。
- wedge・putterはSTEP30時点でこれほど極端な偏りが確認されなかったため、今回は変更していない。
- 新規発見された商品は、既存のロジック（`_is_safe_to_auto_publish`・`_looks_like_accessory`・`MIN_DISCOVERY_PRICE`等）にそのまま従う——中古品・付属品を除外し、実勢価格が妥当な商品のみ、価格1万円以上のクラブは自動公開、それ以外は承認待ちという既存ルールは一切変更していない。

**検証結果**：
- `tests/test_discovery.py`（13件、キーワードリストを`CATEGORY_SEARCH_KEYWORDS["driver"][0]`のようにインデックス参照する設計のため、末尾への追加で既存テストは無傷）を実行し全件成功を確認。
- `pytest`全体実行、213件成功・2件失敗（`cryptography`パッケージ欠損によるこのローカル環境固有の問題、STEP28〜30と同一の既知事象、今回の変更とは無関係）。
- キーワード追加によるジョブ実行時間への影響は、楽天APIのレート制限（1.1秒/リクエスト）換算で+6.6秒程度であり、直近の実行時間（約9分、うち大半は162商品の価格再取得）に対して無視できる増分であることを確認。本番のRakuten API・GitHub Actions実行環境にはこのセッションから直接アクセスできないため、実際の楽天検索結果そのもの（PING等が本当に上位30件に入るか）は次回の本番自動実行で確認する必要がある。

**社長側で必要な作業**：**無し**。次回の日次自動実行（毎朝6時、またはRenderの管理画面「今すぐ検出」ボタンで即時実行も可能）から自動的にこのキーワードが使われる。今後、別のブランド・カテゴリで同様の偏りに気づいた場合も、同じ理由（汎用キーワードが特定ブランドの露出に負けている）である可能性が高いため、`CATEGORY_SEARCH_KEYWORDS`にブランド名キーワードを追加するだけで、CSV手動追加をせずに恒久的に解消できる。

### 3.5.25 War Roomの7人体制拡張・エラーログ調査と自動クリーンアップ・リトライ強化（STEP34、2026-09-25）

**背景**：3件セットの依頼——(1) AI Executive War Roomを7人体制（CEO/CSO/CRO/CPO/CMO/Editor/Compliance）へ拡張、(2) CPO AIが報告していた「直近のログに99件のエラーがあります」の原因調査と解消、(3) 今後のためのエラー自動クリーンアップ・リトライ処理・「AI自動修復」機能の実装。

**調査結果（99件のエラーの原因）**：このセッションの実行環境からは本番DBに直接接続できないため、実際の99件のログ内容そのものは確認できていない。ただしコードレビューにより、再現性の高い根本原因を2つ特定した。
1. **リトライ機構が皆無だった**：`fetch_rakuten_prices`/`fetch_yahoo_prices`（`app/pipeline.py`）は、本番約170商品それぞれに対して個別にRakuten/Yahoo検索を1回ずつ呼び出し、一時的なタイムアウトや5xx/429エラーも即座に`ErrorLog`（level="error"）として記録していた。1日あたり数件の一時的な通信エラーでも、蓄積すれば数週間で二桁〜三桁件になり得る。
2. **ログの自動削除機構が皆無だった**：`ErrorLog`テーブルには作成のみがあり、削除・アーカイブ処理が一切存在しなかった。日次バッチが毎日実行される以上、一時的なノイズ（info/warningレベルの「該当商品なし」「価格乖離検出」等の定型メッセージ含む）が無期限に積み上がる設計になっていた。
3. **潜在的なバグ**：Rakuten/Yahooの検索結果に稀に`itemPrice`/`itemUrl`/`itemName`（Yahoo側は`price`/`url`/`name`）が欠けたリスティングが含まれるケースがあり、これが起きると`_item_to_result`が素の`KeyError`を送出し、該当商品1件のバッチ処理全体が「error」ログとして記録されていた（`fetch_ranking`には既に同種の防御的スキップ処理があったが、価格検索の2関数には無かった）。

**実装内容（2. エラーの解消）**：
- `app/http_retry.py`を新設し、Rakuten/Yahoo双方の検索リクエストに、一時的な失敗（タイムアウト・接続エラー・429/5xx）に対して最大2回・短い間隔でのリトライを追加。最終的にまだ失敗している場合は、呼び出し元の既存のエラーハンドリング（レスポンスをそのまま返す）に委ねるため、エラーメッセージの形式・既存テストへの影響は無い。
- `app/rakuten.py`・`app/yahoo.py`の検索結果パースに、必須フィールド欠落リスティングを黙ってスキップする防御的フィルタを追加（`fetch_ranking`の既存パターンを踏襲）。これにより、1件の不正なリスティングがバッチ全体の該当商品の価格取得を失敗させることがなくなった。

**実装内容（3. 自動クリーンアップ・「AI自動修復」）**：
- `crud.cleanup_error_logs(db, retention_days)`を新設：レベルごとに指定した保持日数を超えたログ行を削除する汎用関数。
- **自動クリーンアップ**：本番の日次バッチの実際のエントリーポイントである`POST /api/admin/fetch-rakuten`（`app/routers/admin.py`、GitHub Actionsが毎朝呼び出す実処理）の最後に、`{"info": 14, "warning": 14, "error": 30}`の保持期間で自動的に古いログを削除する処理を追加した（失敗しても日次バッチ自体は止めない設計）。`scripts/update_prices.py`（手動実行用の補助スクリプト）にも同じ処理を追加し、整合性を保った。
- **「AI自動修復」ボタン**：新設の管理API`POST /api/admin/auto-fix-logs`（Compliance/CPO担当としてWar Room UIのヘッダーに⚖️ボタンを追加）は、info/warningログを保持期間0日（＝即時全削除）、errorログを3日超のもののみ削除する、より即効性のあるクリーンアップを実行する。直近3日以内のerrorログは意図的に残す——「軽微なノイズの一括クリア」であって「現在進行中の問題を隠す」機能ではないことを保証するため。実行結果（削除件数・残存件数）はそのままWar RoomのチャットにCompliance AIの発言として real な数値で表示される。

### 3.5.31 本番エラーログの実データ調査と3件の根本原因修正（STEP40、2026-09-26）

**背景**：「エラーログの内容を確認し、改善対応まで進めて」との依頼を受けたが、このセッションの実行環境からは本番DB・本番URLへの通信がブロックされているため直接ログを取得できない旨をお伝えしたところ、社長が`/admin/logs`の実際の内容（2026/9/25 21:55〜21:57 JST、計約31件）を貼り付けてくださった。続けて「これを毎日自動で改善修正するシステムを作ってほしい、すでにある？」との依頼を受けた。

**調査結果（実ログから特定した3つの根本原因）**：
1. **`popularity`：driver/iron/wedge/putter/ball全5カテゴリで同一の楽天ランキングAPIエラー**（`Rakuten Ranking API 400: {"error_description":"specify valid applicationId","error":"wrong_parameter"}`）。WebSearchで楽天の公式ドキュメント（バージョン2022-06-01）を確認した結果、`app/rakuten.py`の`RANKING_URL`定数が、旧世代（2017-06-28版）のドメイン`app.rakuten.co.jp/services/api/...`と、新しい2022-06-01のバージョン番号を組み合わせた**実在しない不正なURL**になっていたことが原因と判明（同じファイル内の検索APIで使っている`openapi.rakuten.co.jp/ichibams/...`は正しく稼働中で、ランキングAPI固有の設定ミス）。`applicationId`自体は有効な値であり、URLの組み合わせ自体が誤っていたため、5カテゴリ全てで同じ汎用エラーが出ていた。
2. **`price_fetch`：Yahoo!ショッピングAPIで約25件の同一エラー**（`Yahoo Shopping API 429: {...}"The AppID is denied: total count of AppID reached the URL's limit count."`）。これは一時的なレート制限ではなく、**その日のAppID通信回数の上限に達した恒久的な状態**（枠が空くまで何度リトライしても同じ結果になる）。既存のSTEP34リトライ機構は429を「一時的な失敗」として一律リトライ対象にしていたため、枠切れ後も1商品ごとにリトライ→失敗→次の商品でも同様、を繰り返し無駄な通信とログの水増しを起こしていた。
3. **`discovery`：「ブリヂストン TOUR B ゴルフボール」1件のみのエラー**（`Rakuten API 400: {"error_description":"keyword is not valid"...}`）。WebSearchで楽天の検索キーワード仕様を確認した結果、**半角スペース区切りの各単語は「半角2文字以上、または全角1文字以上」である必要がある**という制約があり、単独の半角1文字である`"B"`がこの条件を満たさずリジェクトされていたことが原因。

**実施した修正**：
1. `app/rakuten.py`の`RANKING_URL`を、WebSearchで確認した正しいエンドポイント`https://openapi.rakuten.co.jp/ichibaranking/api/IchibaItem/Ranking/20220601`に修正。
2. - **既にあるもの**：STEP34で実装済みの「リトライ機構（一時的な通信エラーを吸収）」「エラーログの自動クリーンアップ（3日超の`error`ログを日次バッチ末尾で自動削除）」「AI自動修復ボタン（軽微なログの一括クリア）」に加え、STEP38の「毎朝のAI会議レポート」が、エラー件数・日次バッチ結果を実データのまま毎朝メールで報告する仕組みとして既に稼働しており、これらを合わせると「検知→整理→報告」は既に自動化されている。
- **今回追加したもの**：上記3件はいずれも実際のログから特定した具体的なコードバグであり、コードを直接修正することでしか解決しない性質のため、Claudeが調査してコードを修正・テスト・プッシュする形で対応した。加えてYahoo側は「同じ種類のエラーが今後また起きても、バッチ全体を巻き込まず1回のログで済む」という再発時の被害を抑える仕組み（サーキットブレーカー）を恒久的に組み込んだ。

### 3.5.32 X無料APIプラン制限への対応：手動投稿用テキストの自動生成に運用方針転換（STEP41、2026-09-26）

**背景**：STEP40の直後、社長がX開発者アカウントでAPIキーを取得し、Renderのバックエンド環境変数（`X_API_KEY`/`X_API_SECRET`/`X_ACCESS_TOKEN`/`X_ACCESS_TOKEN_SECRET`、Read and Write権限）を設定してくださったため、X自動投稿の動作確認・本番運用準備を依頼された。このセッションからは本番URL・実際のXキーへアクセスできないため、ローカルでの文面生成ロジック検証（既存テスト15件のパス、ルールベース文面のプレビュー生成確認）を行った上で、実際の投稿テストは本番の管理画面「今すぐ投稿」ボタンから社長ご自身に実行していただくようご案内した。その結果、「X APIの無料プランでは投稿自体ができない（402 Payment Required）」ことが判明し、運用方針を「API経由の完全自動投稿」から「そのままコピペ投稿できる完成されたテキストを自動生成し、人間が手動でXに貼り付ける」方式へ転換する依頼を受けた。

2. **402エラーのグレースフルフェイル化**：`XPostError`に`status_code`属性を追加し、`post_tweet()`がAPIエラーのステータスコードを保持するように変更。`post_daily_deals()`は402を検知すると、従来の「エラー」ログ（levelが`error`）ではなく、手動投稿用テキストを添えたinfoレベルのログ（「X API 402（無料プランでは投稿できません）のため自動投稿をスキップし、手動投稿用テキストを生成・ログ出力完了」）を残して正常終了するようにした——402は解消されない恒久的な状態であり、一時的な障害として社長を毎日アラートで煩わせるべきではないため。402以外の失敗（認証エラー・通信エラー等）は従来通りerrorレベルで記録され、区別される。
3. **毎朝のAI会議レポートへの統合**：`app/daily_report.py`に「X投稿用テキスト（コピペ用）」セクションを追加し、`build_manual_post_text()`の結果をメール本文にそのまま埋め込むようにした（X APIキーの設定有無に関わらず、常に生成・表示される——コピー用テキストの生成自体はAPI呼び出しを伴わないため）。
4. **管理画面の改修**：新規の読み取り専用エンドポイント`GET /api/admin/x-post-preview`（認証必須、管理画面共通の`require_admin`で保護）を追加し、「今日のお買い得情報をXに投稿」カードに手動投稿用テキストのプレビュー（`<textarea readOnly>`）とワンクリックコピーボタンを配置した。既存の「今すぐ投稿（API経由）」ボタンは、将来Xの有料プランに移行した場合に備えてそのまま残し、ボタンラベルに「無料プランでは失敗します」と明記した。

**検証結果**：新規追加テスト5件（`build_manual_post_text`が自動投稿と同一テキストを返すこと・商品が無い日は`None`を返すこと、402が`error`ログではなく`info`ログとして手動投稿用テキスト付きで記録されること、`GET /admin/x-post-preview`エンドポイントの認証・レスポンス）を含む全258件のバックエンドテストが成功。フロントエンドは`npx tsc --noEmit`・`npm run lint`・`npm run build`いずれも問題なし。ローカルでバックエンド・フロントエンド双方を実際に起動し、Playwrightで管理画面にログインした上で、テキストエリアに実際の商品データに基づく投稿文（`本日のお買い得情報\nPING G430 MAX ドライバー が¥58,000（定価より-26.8%）\n#ゴルフ #ゴルフクラブ\nhttps://...`）が正しく表示されること、「コピー」ボタンを押すと「コピーしました。」の確認が出ることを実機確認した。

**社長側で必要な作業**：無し。次回の日次自動実行（毎朝6時）・毎朝のAI会議レポートから新しいテキストが反映され、管理画面はいつでもプレビュー・コピーできる状態になっている。

### 3.5.34 アフィリエイトマーケティングの専門知見の組み込みと成果直結の優先度ロジック（STEP43、2026-09-26）

**背景**：Search Consoleの設定完了を受け、「AI幹部とコンテンツ生成エンジンにプロのアフィリエイトマーケターの知見（SEO/CRO/セールスコピー）を組み込み、GA4/Search Consoleのデータから成果に直結する改善をAIが優先的に判断・自動実行できるようにしてほしい」との依頼を受けた。

1. **Search Consoleのデータが商品と結合されていなかった**：Search Console APIのページキーは完全URL、GA4はパスで返すため、スナップショットの行が別々に保存され、Search ConsoleのCTR・掲載順位は商品に紐付かず、改善判断に一度も使われていなかった。`content_metrics._normalize_path`で両方をパスに正規化して修正。テストのモックを実APIの形式（完全URL）に合わせ、旧コードで失敗することを確認した上で修正を適用した。

**実装内容**：
1. **`app/marketing_playbook.py`（新設）**：全てのAI文章生成が従う知見を1か所に集約。
   - SEO（検索結果でクリックされるタイトル）：実際にそのページが表示されている検索語との一致、ブランド名＋商品名を先頭に、全角30文字前後、実データに基づく価値提案は1つ、詰め込みをしない。

### 3.5.35 効果測定で悪化と判定した自動リライトの自動差し戻し（STEP44、2026-09-26）

**背景**：STEP43の報告時に「次の一手として、効果測定で『悪化』と出た変更を自動で元に戻す仕組みにするのが自然」とご提案し、社長から「すすめて」とご承認いただいた。STEP42の時点では「悪化」と判定されても記録と警告表示のみで、元に戻すには社長が管理画面のボタンを押す必要があった。

**判断基準（自動で元に戻す条件、すべて満たす場合のみ）**：
1. 対象は商品説明の自動リライト（`rewrite_product`）のみ。トップページの並び替えは毎日実データで作り直されるため対象外、新規ガイドは取り消し＝記事の非公開化となり影響が大きいため対象外（従来通り社長の判断）。
2. 7日後の効果測定の判定が「悪化」：検索CTR（Search Consoleのデータがある場合）またはPVが、変更前より10%以上低下（STEP42の判定基準をそのまま使用）。
3. 変更前後の数値が十分な実データに基づく：検索CTRで判定した場合は変更前・変更後とも検索表示20回以上、PVで判定した場合は変更前のPVが10以上（いずれも改善候補の検出に使っている最低基準と同じ）。少ないサンプルの偶然の変動で文面を差し戻さないため。
4. 測定期間中ずっと、その自動リライトの文面が表示されていた（別の再生成で置き換わっていた場合はSTEP43の通り「判定不能」となり、そもそも悪化判定されない）。

条件3を満たさない「悪化」は、判定結果を記録したうえで「（サンプル数が少ないため自動では元に戻していません）」と明記し、社長の判断に委ねる。

**元に戻すときの処理**（`app/content_optimizer.py`の`_auto_revert_worse_rewrite`）：
1. 変更前の文面（`content_before`）を復元し、施策の目印（`ai_copy_source_action_id`）を外し、施策を「元に戻し済み」（`revert_reason="auto_worse"`）として記録する。
2. **すぐに最新の価格データで通常の文面を再生成する**。変更前の文面は7日以上前のもので、当時の価格が書かれている可能性があるため、そのまま表示し続けると「現在の価格」と誤認させるおそれがある（景品表示法上のリスク）。再生成に失敗した場合も差し戻し自体は有効なまま、次回の日次更新で再生成を再試行する。
3. 効果測定の記録に「→ 悪化と判定したため自動で元に戻し、最新の価格データで通常の文面に再生成しました」と追記し、ログにも警告レベルで「自動差し戻し」を残す。「悪化した」という判定結果とその数値は削除せず、ナレッジとして残る。
4. 差し戻した商品は7日間、再リライトの対象から外す（差し戻し後の新しい数値で改めて判断するため。これが無いと、同じ日の実行で差し戻し直後に別の文面へ書き換えてしまうことをテストで確認した）。

**費用（絶対ルール1）**：手順2の再生成はClaude APIを1回呼ぶ場合があるため、その日の自動リライトの上限（1日3件）から自動差し戻しの件数を差し引く。1日のClaude呼び出し回数の上限は変わらない。

**社長への報告**：毎朝のAI会議レポートでは、自動で戻したもの（「↩ N件は悪化と判定したため自動で元に戻し…」）と、悪化だが自動では戻していないもの（「⚠ …管理画面から確認してください」）を分けて表示する。War Room（Editor）の発言と管理画面の実施履歴（「自動で元に戻し済み」のラベルと説明）、「今すぐ実行」ボタンの結果表示にも同じ内容が出る。管理画面の手動の「元に戻す」ボタンも、同じ古い価格のリスクがあるため、次回の日次更新で最新データから文面を再生成するようにした。

**検証結果**：新規・更新テストを含む全340件のバックエンドテストが成功（PV・検索CTRそれぞれでの悪化時の自動差し戻しと再生成、サンプル不足時は差し戻さないこと、改善時は差し戻さないこと、再生成失敗時も差し戻しは残り次回再試行されること、上限からの差し引き、差し戻した商品を同日に再リライトしないこと、手動差し戻しの記録、AI会議レポートの表示）。差し戻した商品を再リライトしないテストは、修正を外すと失敗することを確認した。`ruff check`は既存の`schemas.py`の1件を除き警告ゼロ、フロントエンドは`tsc`・`lint`・`build`いずれも問題なし。今回の画面の変更は表示文言のみのため、Playwrightでの実機確認は行っていない。

**DB変更**：`ai_optimization_actions.revert_reason`（NULL可）を追加。`scripts/init_db.py`の`ADDED_COLUMNS`に登録済みのため、次回のRenderビルド時に自動で追加される。

**社長側で必要な作業**：無し。STEP42の最初の自動リライトが7日を経過した日の日次自動実行から適用される。

### 3.5.36 X投稿文面のCTR重視化とOGP画像の修復（STEP45、2026-09-26）

**背景**：「X手動投稿用のプレビューテキストとサイトのOGP設定を、SNSでのクリック率・インプレッションを最大化するプロ仕様に改修してほしい」との依頼。文面は「本日のお買い得情報…」という事実の羅列からフック・直感的なお得感・CTA・絵文字を取り入れた形式へ、OGPはXでリンクを貼った際にグレーのアイコンにならず魅力的なカード画像が出るように、という2点。

**調査で判明したグレーのカードの原因**（ローカルで本番ビルドを起動し、実際に出力されるタグと画像を確認）：
1. **カテゴリページとガイド記事ページに`og:image`が1つも無かった**。Next.jsでは、ページ側の`generateMetadata`で`openGraph`を設定すると、上位（サイト共通）の画像設定が引き継がれずに消える。トップ・商品・/deals等には画像が出ていたが、`/category/*`と`/guides/*`は`twitter:card`だけで画像が無い状態だった。
2. **2商品を紹介するX投稿は常にカテゴリページにリンクしていた**ため、1の影響をそのまま受けていた。しかも2商品のカテゴリが異なる場合（ドライバー＋ボール等）、1本目のカテゴリページにリンクしており、2本目の商品はリンク先に載っていなかった。
3. 予防的な修正：`NEXT_PUBLIC_SITE_URL`がビルド時に未設定だと、`og:image`のURLが`http://localhost:3000/...`になり全てのカードがグレーになる設計だった（`NEXT_PUBLIC_*`はビルド時に固定されるため、設定漏れがあると気付きにくい）。
4. 構造的なリスク：Renderの無料プランではバックエンドが休止し、復帰に数十秒かかる。その間にXがカード画像を取りに来ると、商品データの取得を待っている間にXの取得がタイムアウトしてカードが出ない。Xは一度取得したカードをしばらくキャッシュするため、影響が残る。

なお、日本語の文字化け（フォント未対応）は発生していないことを実際の生成画像で確認した。

**OGP画像の修正内容**（`frontend/lib/og.tsx`に共通部品を集約）：
- `app/category/[category]/opengraph-image.tsx`（新設）：「今日の{カテゴリ}お買い得」＋追跡商品数＋買い時スコア上位商品の写真。
- `app/guides/[slug]/opengraph-image.tsx`（新設）：ガイド記事のタイトル・説明文。
- 商品ページの画像を刷新：商品写真（楽天の画像は600px指定で取得）、大きな価格表示、「定価より¥59,400安い（-38%）」、右上の見出し（下記の事実条件を満たす場合のみ）、買い時スコア。写真が無い商品は従来のスコア表示のまま。
- **絶対にエラーにしない**：商品データの取得は5秒、商品写真は3秒でタイムアウトし、失敗した場合も「PAR.」のブランド入り画像を返す。写真はPNG/JPEGのみ使用し、それ以外の形式や2MB超の画像は使わずにレイアウトする（画像1枚の不具合でカード全体が出なくなることを防ぐため）。
- `frontend/lib/siteUrl.ts`（新設）：本番ビルドで`NEXT_PUBLIC_SITE_URL`が未設定でも`https://par-gear.com`を使う。layout・robots・sitemap・各ページのcanonicalも同じ値に統一した。

**投稿文面の刷新**（`backend/app/x_post.py`）：
- 型：フック（1行目）→ 商品名 → 価格とお得額 → 買い時スコア → （2本目の紹介）→ CTA「相場推移と取扱店舗はここからチェック👇」→ URL → ハッシュタグ（#ゴルフ＋カテゴリ＋ブランド）。
- **リンクは常に1本目の商品ページ**（商品写真・価格・同じ見出しが入ったカードが表示される）。「1投稿1メッセージ1リンク」とし、2本目は本文で紹介するのみ。
- **フックは事実で裏付けられる場合にだけ出す**（強い順に1つ）：
  - 「過去N日間の最安値に」：現在価格が記録上の最安値以下、かつ価格履歴7日以上。
  - 「定価の半額以下に」：割引率50%以上。「ほぼ半額に」：45%以上。**判定は四捨五入前の正確な割引率で行う**。
  - 「定価から33,100円引き」：割引率30%以上。
  - 「30日平均より8.2%ダウン」：価格履歴7日以上で、30日平均より5%以上安い。
  - 主語に「楽天ランキング3位の{カテゴリ}」：楽天の売れ筋ランキングの実順位（30位以内、3日以内に取得したもののみ）。それ以外は「注目の{カテゴリ}」。
- 依頼例にあった表現の扱い：「衝撃値引き」は数値の裏付けが無い主観的な煽りになるため使わず、実際の値引き額・割引率で表現した。「今週の最安値を更新」はデータ上「今週」「更新（前回より下がった）」を常に正しく言えるとは限らないため、正確に言える「過去N日間の最安値に」とした。

### 3.5.37 商品画像の表示崩れ対策：URL正規化・NO IMAGE代替表示（STEP46、2026-09-26）

**背景**：「par-gear.com上で一部の商品画像やカード画像が表示されない（崩れる・読み込まれない）問題を修正してほしい」との依頼。確認項目として、(1) `next.config`の`remotePatterns`、(2) 画像URLがnull・空文字・読み込み失敗の場合の「NO IMAGE」代替表示、(3) `http://`の画像URLの`https://`化、の3点。

**調査結果**：
- 商品画像の取得元は、楽天（`thumbnail.image.rakuten.co.jp`、`backend/app/rakuten.py`）、Yahoo!ショッピング（`*.yimg.jp`、`backend/app/yahoo.py`）、CSVインポート・管理画面で入力された任意のURLの3種類。`data/*.csv`の`image_url`列は空欄85件と`example.com`（存在しない見本URL）6件のみ。
- **`remotePatterns`は今回の表示不具合の原因ではない**。全ての商品画像は`SafeProductImage`コンポーネントで`unoptimized`（Next.jsの画像最適化サーバーを通さず、元画像をそのまま読み込む）指定になっている。Next.js本体のコード（`image-loader.js`）を確認したところ、`remotePatterns`のチェックは最適化する場合にだけ行われるため、現状の表示には影響しない。
- **読み込み失敗時の代替表示の仕組み自体は既にあった**（失敗時はカテゴリのアイコンに切り替え）。React が画面を操作可能にする前に読み込みエラーが起きた場合の取りこぼしも、Next.js側で対策済みであることを確認した。
- 実際に崩れ・読み込み失敗を起こしうる原因として、次の3点を特定した。
  1. 画像URLの検証が無かった。空白だけの文字列はそのまま画像として読み込まれて壊れた画像になる。`http://`・`//`始まり・相対パス・`data:`等も素通しだった。
  2. 背景の写真コラージュと商品ページの構造化データ（JSON-LD、Googleが読む商品情報）にも、未検証のURLがそのまま使われていた。
  3. 一部の画像サーバーは、他サイトからの参照元（Referer）付きの直リンクを拒否する。これへの対策が無かった。

**実装内容**：
1. **`frontend/lib/imageUrl.ts`（新設）**：`normalizeImageUrl()`で、使える画像URLかどうかを1か所で判定する。
   - null・空文字・空白のみ → 無し（代替表示）
   - `http://`（大文字小文字問わず）→ `https://`に置換
   - `//`始まり → `https://`を付与
   - サイト内パス（`/`始まり）→ そのまま
   - それ以外（`data:`・`javascript:`・`ftp:`・相対パス・不正な文字列）→ 無し
   - 楽天・Yahoo!の画像サーバーはいずれもhttpsで配信している。https化した結果読み込めない画像は、下記の代替表示になる。
2. **`frontend/components/ProductImagePlaceholder.tsx`（新設）**：サイト共通の「NO IMAGE」代替表示。カテゴリのアイコン＋PAR.ロゴ＋「NO IMAGE」の表記で構成する。SVGとCSSのみで画像を読み込まないため、代替表示自体が壊れることは無い。小さいサムネイル（ランキング・比較表）では表記を省いたコンパクト版を使う。
3. **`SafeProductImage`の強化**：URLを正規化してから読み込み、URLが無い・不正・読み込み失敗のいずれでも代替表示に切り替える。
   - 失敗の記録をURLごとに持つようにした。管理画面で画像を差し替えた場合などに、前の画像の失敗を引きずらず再度読み込む。
   - `referrerPolicy="no-referrer"`で、直リンクを拒否する画像サーバー対策をした。
   - 全6か所の呼び出し元（商品カード・注目商品カード・商品詳細・ランキング2か所・比較表）の「URLがあれば画像、無ければアイコン」という個別の分岐を撤去し、判定を`SafeProductImage`に一本化した。
4. **写真コラージュ・JSON-LD・OGP画像（STEP45）にも同じ正規化を適用**した。構造化データに`http://`や不正なURLが入ることは無くなった。
5. **`next.config.ts`に`images.remotePatterns`を追加**：楽天（`thumbnail.image.rakuten.co.jp`、`image.rakuten.co.jp`、`shop.r10s.jp`、`tshop.r10s.jp`）とYahoo!（`item-shopping.c.yimg.jp`、`shopping.c.yimg.jp`、`**.yimg.jp`）を、https限定で登録した。
   - 上記の通り、現状の`unoptimized`表示には影響しない。将来、画像最適化を有効にする場合の許可リストとして、実際の取得元に合わせて登録した。
   - 最適化を有効にしない理由は2つある。フロントエンドはRenderの無料インスタンスで動いており、全画像を最適化サーバーに通すとCPU・メモリの負荷が大きい。また、管理画面で任意のURLを登録できるため、許可リストに無い取得元の画像が表示されなくなる。

**検証結果**：
- URL正規化の15パターン（null、空文字、空白、`http`、`HTTP`、前後の空白、`//`始まり、サイト内パス、相対パス、`javascript:`、`data:`、`ftp:`、`https://`のみ、不正な文字列など）をNode.jsで実行し、全て期待通りだった。
- `tsc`・`lint`（既存の警告1件のみ）・本番ビルドとも問題なし。
- ローカルで本番ビルドを起動し、Playwrightで確認した。商品に「正常な画像」「`http://`のURL（https化後に読み込めない）」「空文字」「空白のみ」「`example.com`の存在しない画像」「null」を設定し、カテゴリ・商品詳細・比較・ランキングの各ページを表示した。
  - **壊れた画像の表示は全ページで0件**だった。正常な画像は表示され、それ以外は全て「NO IMAGE」の代替表示になった。
  - 画面上の`<img>`に`http://`の外部URLが残らないことを確認した。
  - カードのレイアウトが崩れないことをスクリーンショットで確認した。

**社長側で必要な作業**：無し（次回デプロイから反映）。

### 3.6 整理可能な不要データ／保持すべき重要データ

### 3.7 Claude Code用カスタムスキル（STEP20、2026-09-22）

**背景**：これまでのSTEPで確立した設計・ルール（商品名クレンジング、安全なDBマイグレーション、X投稿プレビュー）を、
毎回ゼロから説明し直すのではなく、Claude Codeの再利用可能な「スキル」として定義し、今後の運用トークン削減・
他Webメディアへの横展開時の再利用を高速化する。

**実装内容**：リポジトリ直下 `.claude/skills/` 配下に、各スキル用ディレクトリと`SKILL.md`を新規作成した

1. **`clean-product-title`**（`.claude/skills/clean-product-title/SKILL.md`）：`app/title_cleaner.py`・

   追加パターンをまとめた。DBへの実際の書き込みは対象外（`safe-db-migration`が担当）と明記。
2. **`safe-db-migration`**（`.claude/skills/safe-db-migration/SKILL.md`）：STEP15/16で確立した
   「`app/<name>_migration.py`（本体ロジック）＋`scripts/<name>_migration.py`（CLIラッパー）＋
   管理APIエンドポイント（`require_admin`保護）」という三位一体のパターンをテンプレート化。

## 4. 運用メモ

- 本番URL: `https://golf-deals-frontend.onrender.com`
- 日次バッチのトリガー: GitHub Actions（Renderの無料プランはスリープするため、外部からのcronで叩く構成。Renderの有料Cron Jobsは使っていない — 3.1参照）
- **日次ジョブの状況確認方法**：
  1. GitHub Actionsの実行履歴（リポジトリの「Actions」タブ→「Daily price update」）。各実行のStep Summaryに結果JSONが表示される。
  2. 管理画面の「ログ」ページ（`/admin/logs`）。最新のジョブ実行結果が`source: daily_job`の1行に要約されている（新しい順に並ぶので一番上）。
  3. GitHub Actionsのスケジュール実行が失敗した場合、GitHubがリポジトリオーナーに自動でメール通知する。
  - **注意**：GitHub Actionsのスケジュール実行は、リポジトリに60日間コミットが無いと自動的に無効化される仕様がある（GitHub側の一般的な挙動）。長期間コードの変更が無い場合は、手動で`workflow_dispatch`を1回実行するか、空コミットではなく実際の変更をpushして再有効化する必要がある。
- 環境変数の秘密情報（APIキー等）はRenderの環境変数に設定し、チャット等には貼らない運用とする。
