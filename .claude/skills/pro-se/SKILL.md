# SE部の専門スキル

## 1. テクニカルSEOの点検順（上ほど影響が大きい）
1. **見つけてもらえるか**：robots.txt、sitemap.xml（実在するURLだけ・200を返すURLだけ）、内部リンクから届くか。
2. **登録されるか**：noindex・canonicalの誤り、重複ページ（並び替え・絞り込みのURL）、ソフト404（商品0件のページ）。Search Consoleの「クロール済み・未登録」「検出・未登録」の数を事実として使う。
3. **正しく読めるか**：サーバー側で描画した本文に、価格・商品名・見出しが入っているか（JavaScriptを待たないと出ない内容は不利）。
4. **速さ**：Core Web Vitals（LCP 2.5秒以内・INP 200ms以内・CLS 0.1以下が「良好」の目安）。Renderのスリープ明けの遅さは、初回表示（TTFB）として分けて測る。
5. **構造化データ**：Product・Offer・BreadcrumbList。表示中の価格と一致させ、在庫・価格の時点を持たせる。

## 2. 見つけた問題の並べ方（トリアージ）
影響（流入・報酬への距離）×広さ（何ページに起きるか）÷工数 で並べる。件数が多いだけの軽微な警告は後回しにし、理由を1行書く。

## 3. 工数見積もり（他部署の提案のレビュー）
- 作業を「調べる・作る・テスト・本番確認」に分け、それぞれ時間で書く。合計に不確かさ（±何%）を付ける。
- 「元に戻せるか」「本番データに触るか」「日次ジョブ（6:00）と重なるか」を必ず書く。本番データは`safe-db-migration`の手順。

## 4. 安定運用とセキュリティ
- 障害は「いつ・何が・どれだけ・原因・再発防止」で記録する。同じ失敗が2回起きたら、仕組み（自動テスト・監視）の提案にする。
- 秘密情報はコード・ログ・公開リポジトリに出さない。依存パッケージの既知の脆弱性は、重大度と実際に使っている箇所で判断する。

## 5. 意見書の質の基準
- 変更するファイル・関数名まで書く。効果は「何が何件直る／何秒速くなる見込み」。測り方（どの数字を、いつ比べるか）も書く。
